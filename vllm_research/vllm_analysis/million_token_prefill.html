百万序列 Prefill：vLLM 如何解决 + 仍开放的难题

0. Executive Summary

核心命题：当单请求序列长度达到 100K–1M token 时，prefill 阶段（计算完整 self-attention）同时撞上 计算墙（O(n²) attention）、存储墙（KV Cache 容量）和 带宽墙（HBM 读写）。vLLM 通过 6 条技术路线组合应对——但每条路线都有其物理极限，百万级 prefill 仍是开放问题。

已解决 (工程级)

  • Chunked Prefill 避免 batch 内长 prefill 饿死 decode
  • DCP (Ring Attention) 多卡切分 decode 阶段 KV
  • KV Offload 到 CPU / P2P 二级存储
  • MLA 压缩 KV Cache ~57x (DeepSeek-V3)
  • Prefill-Decode 分离部署 (DistServe 范式)

仍开放 (物理级)

  • Attention O(n²) 计算量 — 1M token 单请求需 10¹² FLOPs/layer
  • KV Cache 容量 — 1M token × 60 层 × 576B = 34.6 GB (MLA)
  • CP 通信开销 — Ring Attention 全随 world_size 线性增长
  • Sparse Attention 质量-效率权衡
  • Prefill TTFT 下限 — 受 roofline 约束
关键洞察：vLLM 的策略是"没有银弹，只有组合"——Chunked Prefill 解决调度公平性但不减少总计算；CP 分摊存储但增加通信；MLA 压缩存储但引入解压开销；Offload 扩展容量但受限于 PCIe 带宽。百万级 prefill 的终极解决需要算法-系统-芯片协同设计。

1. 物理墙：为什么百万 Prefill 是难题

1.1 三条物理约束

约束公式1M token 单请求含义
Attention 计算$2 \times n^2 \times d$$2 \times 10^{12} \times 128 = 256$ TFLOPs/layer即使 H100 1979 TFLOPS fp8, 单 layer 需 130ms
KV Cache 存储$n \times L \times (2 \times d_{kv} \times n_h)$$10^6 \times 60 \times 32768$B = 1.87 TB (MHA)远超单卡 HBM
MLA KV Cache$n \times L \times (d_{lora} + d_{rope})$$10^6 \times 60 \times 576$B = 34.6 GB单卡 H200 141GB 可容纳
Prefill 带宽$\frac{2 \times n \times d \times n_h}{BW_{HBM}}$$\frac{2 \times 10^6 \times 128 \times 128}{3350 GB/s} \approx 98$ ms仅 model weight 读取
物理第一定律：Attention 的 O(n²) 计算量是信息论下界——每个 token 必须与所有前序 token 交互以建模完整上下文。任何"跳过"某些交互的优化（sparse attention）都意味着信息损失。MLA 不减少计算量，只压缩存储。

2. Chunked Prefill：时间换空间

2.1 机制

vLLM v1 默认启用 Chunked Prefill (enable_chunked_prefill=True)。核心思想：将长 prefill 切成多个 chunk，与 decode 请求交错执行，避免长 prefill 阻塞 decode 的 TTFT。

2.2 调度哲学

vLLM 的设计哲学 (scheduler.py:430-438)："There's no 'decoding phase' nor 'prefill phase' in the scheduler. Each request just has num_computed_tokens and num_tokens_with_spec." — 统一调度模型，chunked prefill 只是 num_computed_tokens 逐步追赶 num_tokens_with_spec 的自然结果。

2.3 关键参数与权衡

参数作用调大调小

long_prefill_token_threshold长 prefill 截断阈值单步 prefill 更快decode 请求更易被饿死

Chunked Prefill 的物理极限：它不减少总计算量——1M token 的 prefill 总 FLOPs 不变，只是分摊到多个 step。总 prefill 时间 = roofline 决定的计算时间，chunking 只影响 TTFT 和 decode 延迟，不改变总墙钟时间。对于单请求 1M token，即使 H100 全速运行，attention 计算本身就需要数十秒。

DCP 是 vLLM 对 Ring Attention 的实现——将 KV Cache 按序列维度切分到 N 张卡，每张卡只存储 1/N 的 KV，通过 ring-all-gather 通信实现完整 attention。

vLLM 实现了两种 DCP 通信后端：

3.3 PCP 的退场

PCP 正在被移除：最近 commit [Refactor][PCP][1/N] remove PCP from MRV1 (#12592) 和 [DOC][CI]take the PCP-related documents offline (#12728) 标志着 PCP 在 vLLM-Ascend 中被废弃。原因：(1) PCP 需要 prefill 阶段跨卡同步，延迟高；(2) DCP 的 Ring Attention 在 decode 阶段更高效；(3) 长 prefill 的瓶颈在计算而非存储，PCP 不解决根本问题。

3.4 CP 的物理极限

CP 的通信开销模型：对于 N 卡 DCP，每步 decode 需要 ring-all-gather 通信量为 $\frac{N-1}{N} \times KV_{total}$。当 N=8、序列 1M token、MLA 576 bytes/tok/layer：
  • 单步通信量 = 7/8 × 1M × 576B × 60 layers = ~28.4 GB
  • NVLink 600 GB/s → 每步 47ms 通信开销
  • 随 world_size 线性增长 → 扩展到 16/32 卡时通信主导
结论：CP 分摊存储但不减少总计算；通信开销限制扩展效率；对 prefill 阶段（计算主导）帮助有限。

4. MLA：KV Cache 压缩的范式革命

4.1 机制

Multi-head Latent Attention (MLA) 是 DeepSeek-V2/V3 的核心创新——通过低秩压缩将 KV Cache 从 $O(n_h \times d_h)$ 压缩到 $O(d_{lora} + d_{rope})$。

标准 MHA (128 heads × 128 dim)$128 \times 128 \times 2 = 32768$ bytes1.87 TB1x

MLA 的物理意义：57x 压缩率意味着单张 H200 (141GB HBM) 可以容纳 ~2.4M token 的 MLA KV Cache (60 layers)。这是 DeepSeek-V3 能在生产环境支持 128K+ 上下文的关键。但 MLA 的计算量不减少——attention 仍是 O(n²)，只是 KV 存储和读取量降低。

4.4 MLA 的解压开销

MLA 的隐藏成本：KV Cache 压缩 57x 意味着每个 token 的 attention 计算需要从 576 bytes 解压回 32768 bytes（通过 kv_b_proj 投影）。这个 O(n × d_lora × d_full) 的解压计算在长 prefill 时不可忽视——对于 1M token，单 layer 解压需要 $10^6 \times 512 \times 32768 \approx 16.8$ TFLOPs，与 attention 本身同量级。

5.6 Offload 的物理极限

PCIe 带宽墙：CPU offload 的加载速度受限于 PCIe 5.0 x16 ≈ 64 GB/s。加载 1M token 的 MLA KV Cache (34.6 GB) 需要 ~540ms——这比 GPU 直接计算 attention 还慢。Offload 只适用于复用场景（prefix caching、跨请求共享），不适合首次 prefill 的长序列。

KV 传输时间估算：1M token × 576 bytes × 60 layers = 34.6 GB。通过 400 Gbps RDMA (Mooncake/Nixl) 传输需要 ~692ms。这比 prefill 计算本身（数十秒）小一个量级，因此 disagg 对长 prefill 是净正收益。

7.3 Sparse 的物理极限

Sparse Attention 的根本矛盾：理论上 sparse attention 可以将 O(n²) 降到 O(n√n) 甚至 O(n)，但：
  • 动态 pattern 需要 runtime 计算 index — 引入额外开销
  • Quality-efficiency tradeoff — 1M token 中选 10K top-k 意味着 99% 的 KV 被丢弃，长程依赖建模受损
  • 硬件不友好 — GPU 对不规则访存效率低，sparse 的加速比理论值差
  • Prefill vs Decode 不对称 — prefill 的 O(n²) 计算是 dense 的，sparse 只对 decode (逐 token) 有显著收益
结论：Sparse attention 是 decode 阶段的利器，但对 prefill 阶段的帮助有限——prefill 需要完整的 Q×K 矩阵乘来生成第一个 token。

8.4 MLA Chunked Prefill Workspace

source: vllm_ascend/attention/utils.py:134-159 · mla_v1.py:485-526

Ascend 的 MLA chunked prefill 使用预分配 workspace 来分批处理长上下文：

# utils.py:134-159 — workspace 大小计算
def ascend_chunked_prefill_workspace_size(vllm_config):
    chunked_prefill_workspace_size = min(
        # 8 个全长请求 或 4 pages/请求
        max(8 * max_model_len, 4 * max_num_seqs * block_size),
        # 长上下文上限 128K tokens
        # 2*(576)*(128*1024) = 288 MB (MLA, fp16)
        # 2*(192*128)*(128*1024) = 6 GB (up-projected)
        128 * 1024,
    )
    return chunked_prefill_workspace_size
# mla_v1.py:501-505 — max_context_chunk 计算
self.max_context_chunk = self.chunked_prefill_workspace_size // num_prefills_with_context_cpu
self.max_context_chunk = round_down(self.max_context_chunk, self.block_size)
self.num_chunks = cdiv(max_context_len_cpu, self.max_context_chunk)
Ascend 的关键设计决策：workspace 上限 128K tokens 意味着单请求 1M token 的 prefill 需要 ≥8 个 chunk。每个 chunk 独立执行 attention 和 KV 写入，通过 chunk_seq_lens 和 cu_seq_lens_cpu 管理分块边界。这是"空间换时间"的典型——用固定大小的 workspace 处理任意长序列。

8.5 Ascend 独有：Sleep Mode + Recompute

Ascend 还实现了两种 vLLM 上游没有的长上下文机制：

机制文件原理
Sleep Modeplatform.py:146空闲时将 KV Cache 交换到 CPU，唤醒时恢复。使用 CaMemAllocator + sleep_persistent_tag
Recompute Schedulerrecompute_scheduler.py不解压/不存储 KV，而是在 decode 时从 hidden states 重新计算 KV。用计算换存储
Lost-in-the-Middle 问题：研究表明（arXiv:2307.03172），长上下文 LLM 的实际可用检索能力峰值在宣传上下文窗口的 50-65%。1M token 的模型实际能有效利用的约 500-650K token。这意味着"支持 1M"≠"有效利用 1M"，系统层面的优化（KV 压缩、offload）需要与算法层面的 attention 质量提升协同。

9.3 工程级难题 (可解决但未解决)

开放工程问题：
  1. MLA 解压与 attention 的 overlap：当前 kv_b_proj 解压在 attention 之前串行执行。如果能将解压与 attention 流水线化（类似 decode 时的 compute-transfer overlap），可隐藏部分解压延迟。
  2. Chunked Prefill 的最优 chunk size：当前 long_prefill_token_threshold 是静态配置。自适应 chunk size（根据当前 batch 中 decode 请求的紧迫度动态调整）是开放问题。
  3. KV Offload 的预取策略：当前 ARC (Adaptive Replacement Cache) 是被动的。如果能预测哪些 block 将被复用（基于 prefix caching 命中率），可以主动预取。
  4. Disagg 的 KV 传输调度：多个 prefill 请求的 KV 传输如何与 decode 节点的消费速率匹配？背压机制尚不完善。
  5. Sparse Attention 的 prefill 适用性：能否在 prefill 阶段使用 learned sparse pattern（如 DeepSeek-V3.2 的 indexer）来跳过不相关 KV？

10.2 组合策略：vLLM 的"全栈"方案

生产级百万 prefill 的推荐组合：
  1. 算法层：MLA (57x KV 压缩) + 可选 Sparse (decode 阶段)
  2. 系统层：Chunked Prefill (调度公平) + DCP (多卡分摊 KV)
  3. 部署层：P/D Disagg (prefill 节点用 H200, decode 节点用 H100)
  4. 存储层：KV Offload to CPU (prefix caching 复用)
  5. 硬件层：H200 141GB / B200 192GB HBM + NVLink + RDMA

10.3 未来路线判断

2026-2027 趋势研判：
  • 短期 (6 个月)：MLA 成为长上下文标配；DCP 扩展到 16-32 卡；Sparse Attention 在 decode 阶段普及
  • 中期 (1-2 年)：CXL 内存扩展打破 HBM 容量墙；HBM4 容量翻倍；Linear Attention 质量逼近标准 Attention
  • 长期 (3-5 年)：光学互连 / 3D 堆叠 HBM / 存算一体 可能从根本上改变 prefill 的计算范式
  • 最被低估的方向：Speculative Prefill——用草稿模型预测 prefill 的 KV 分布，减少完整 attention 计算量（类似 speculative decoding 的 prefill 版本）
