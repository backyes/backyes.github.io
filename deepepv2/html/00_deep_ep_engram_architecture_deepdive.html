Thesis：Engram 是 DeepEP V2 引入的 0 SM RDMA 远端内存访问原语，通过 NCCL Gin (GPU-Initiated Networking) 让 GPU 直接发起 RDMA Get 操作，绕过 CPU 和 NIC 软件栈。其核心设计在于将远端内存抽象为"对称内存窗口"中的全局可寻址表，通过 QP 并行化 + 路由分解 + 原子 flush 控制实现高并发查表，且与模型推理/训练共部署于同一 GPU 进程内。

概述

Engram（Experimental）是 DeepEP V2 中最具创新性的实验特性之一。它实现了 0 SM (Streaming Multiprocessor) 占用的远端内存访问——GPU 通过 RDMA 网络直接读取其他节点的 GPU/CPU 内存，无需占用任何 SM 计算资源进行数据搬运。

核心定位：Engram 面向的场景是 远程 KV Cache 访问——在 Disaggregated Inference（分离式推理）架构中，Prefill 节点的 KV Cache 需要被 Decode 节点远程读取。传统方案需要 CPU 参与（GPU → CPU → NIC → 网络 → NIC → CPU → GPU），而 Engram 允许 GPU 直接通过 RDMA Get 远程读取，实现真正的 GPU-to-GPU 零拷贝。

本报告基于 DeepEP v2.1.0 源码，从以下维度进行深度剖析：

  • 源码架构：Python API → C++ Runtime → CUDA Kernel → JIT 编译 四层结构
  • Gin 交互：NCCL Gin (GPU-Initiated Networking) 的 handle 构造、RDMA Get/Flush 原语
  • RoCE/NVLink 路径：跨节点 RoCE RDMA 与节点内 NVLink 的分流处理
  • 查表并发：多 QP 并行、路由分解、原子计数与 flush 控制
  • 对称内存：HybridElasticSymmetricMemory 的 CPU 段注册与跨进程映射
  • SM 调用 RoCE："0 SM" 的本质与实际 SM 占用分析
  • 部署模型：与模型共部署 vs 独立部署的可行性

1.1 Python API 层

Python 层定义在 deep_ep/buffers/elastic.py 的 ElasticBuffer 类中：

class ElasticBuffer:
    @staticmethod
    def get_engram_storage_size_hint(num_entries, hidden, num_max_tokens_per_rank, dtype):
        """计算 Engram 存储所需的最小 buffer 大小"""
        num_bytes_per_entry = align(hidden * dtype.itemsize, 32)  # LDG.256 对齐
        num_gpu_bytes = align(num_bytes_per_entry * num_max_tokens_per_rank, buffer_alignment)
        num_cpu_bytes = align(num_bytes_per_entry * num_entries, buffer_alignment)
        return num_gpu_bytes, num_cpu_bytes

    def engram_write(self, storage, sf=None):
        """写入 Engram 数据到 buffer（含前后 barrier）"""
        self.runtime.engram_write(storage, sf)

    def engram_fetch(self, indices, num_qps=0, use_tma_aligned_col_major_sf=False):
        """发起远端获取，返回 hook callable"""
        return self.runtime.engram_fetch(indices, num_qps, use_tma_aligned_col_major_sf)

关键设计：

  • get_engram_storage_size_hint：分离 GPU 和 CPU 存储需求。GPU 端只需接收缓冲区（num_max_tokens_per_rank），CPU 端存储全量 entries
  • engram_write：包含 barrier 确保写入对所有 rank 可见
  • engram_fetch 返回 callable：延迟执行模式——fetch 只发起 RDMA，返回的 hook 被调用时才 wait 完成

1.2 C++ Runtime 层

C++ 层在 csrc/elastic/buffer.hpp 的 ElasticBuffer 类中实现核心逻辑：

void ElasticBuffer::engram_write(const torch::Tensor& storage,
                                  const std::optional<torch::Tensor>& sf) {
    barrier(false, true);  // 确保之前 fetch 完成

    // 写入到 CPU 段 (buffer + num_gpu_buffer_bytes + offset)
    const auto cpu_write_offset = allow_hybrid_mode
        ? nccl_context->scaleup_rank_idx * num_cpu_buffer_bytes : 0;
    cudaMemcpyAsync(
        advance_ptr(buffer, num_gpu_buffer_bytes + cpu_write_offset),
        storage.data_ptr(), storage.nbytes(),
        cudaMemcpyDeviceToDevice, compute_stream);

    barrier(false, true);  // 确保写入可见
}

engram_fetch 的 C++ 实现：

auto ElasticBuffer::engram_fetch(const torch::Tensor& indices, int num_qps,
                                  const bool& use_tma_aligned_col_major_sf) const {
    // 1. 准备接收 tensor (zero-copy from GPU buffer)
    auto fetched = torch::from_blob(buffer,
        {num_tokens, engram_hidden * num_entries_per_token}, ...);

    // 2. 准备 Gin request 追踪区
    auto last_gin_requests = torch::empty(
        {num_gin_ranks * num_qps, sizeof(ncclGinRequest_t)}, ...);

    // 3. 发起 RDMA Get kernel
    launch_engram_fetch(
        nccl_context->dev_comm, nccl_context->window,
        advance_ptr(buffer, num_gpu_buffer_bytes),  // CPU 段基址
        fetched.data_ptr(),                          // GPU 接收区
        indices.data_ptr<int>(),
        last_gin_requests, ...);

    // 4. 返回 lambda：调用时执行 wait kernel
    return [=, this]() {
        launch_engram_fetch_wait(last_gin_requests, ...);
        return {fetched, fetched_sf};
    };
}

关键洞察：engram_fetch 使用 torch::from_blob 在 GPU buffer 上零拷贝创建输出 tensor。RDMA Get 直接写入 GPU buffer 的前端，无需额外拷贝。

1.2 CUDA Kernel 层

CUDA kernel 在 deep_ep/include/deep_ep/impls/engram_fetch.cuh 中实现。这是 Engram 的核心：

template <int kNumQPs, int kNumEntriesPerRank, int kNumHiddenBytes,
          int kNumSFPacks, int kNumEntriesPerToken, int kNumRDMAPeers,
          int kNumRanksPerRDMAPeer, size_t kIntraRankStorageStride,
          int kNumThreads, typename team_t, int kNumWarps>
__global__ void __launch_bounds__(kNumThreads, 1)
engram_fetch_impl(const ncclDevComm_t nccl_dev_comm, const ncclWindow_t nccl_window,
                  void* storage, void* fetched, int* indices,
                  ncclGinRequest_t* last_gin_requests,
                  const sf_pack_t* sf_table, sf_pack_t* fetched_sf,
                  const int sf_token_stride, const int sf_hidden_stride,
                  const int num_tokens) {
    const auto qp_idx = blockIdx.x;          // 每个 block = 1 个 QP
    const auto warp_idx = ptx::get_warp_idx();
    const auto global_warp_idx = qp_idx * kNumWarps + warp_idx;

    // 构造 Gin handle
    const auto gin = handle::NCCLGin(nccl_dev_comm, nccl_window, qp_idx,
                                      NCCL_GIN_RESOURCE_SHARING_CTA);

    // 每个 warp 处理一个 token 的 entry fetch
    if (ptx::elect_one_sync()) {
        for (int i = global_warp_idx; i < num_tokens * kNumEntriesPerToken;
             i += kNumQPs * kNumWarps) {
            const auto global_idx = __ldg(indices + i);
            const auto owner_rank_idx = global_idx / kNumEntriesPerRank;
            const auto local_entry_idx = global_idx % kNumEntriesPerRank;

            // 路由到 RDMA peer
            const auto peer_idx = owner_rank_idx / kNumRanksPerRDMAPeer;
            const auto intra_peer_rank_idx = owner_rank_idx % kNumRanksPerRDMAPeer;

            // 计算源地址偏移
            const auto src_byte_offset = int64_t(intra_peer_rank_idx) * kIntraRankStorageStride
                                       + int64_t(local_entry_idx) * kNumHiddenBytes;

            // 发起 RDMA Get
            issue_rdma_get(i, peer_idx, src_byte_offset, ...);
        }
    }
}

Wait kernel 在 deep_ep/include/deep_ep/impls/engram_fetch_wait.cuh：

__global__ void __launch_bounds__(kNumThreads, 1)
engram_fetch_wait_impl(const ncclDevComm_t nccl_dev_comm,
                       const ncclWindow_t nccl_window,
                       ncclGinRequest_t* last_gin_requests) {
    const auto qp_idx = blockIdx.x;
    const auto gin = handle::NCCLGin(nccl_dev_comm, nccl_window, qp_idx, ...);

    // 遍历所有 RDMA peer，等待非零 request 完成
    for (int i = thread_idx; i < kNumRDMAPeers; i += kNumThreads) {
        auto last_gin_req_int4 = __ldg(reinterpret_cast<int4*>(
            last_gin_requests + qp_idx * kNumRDMAPeers + i));
        if (last_gin_req_int4.x != 0 || ...) {
            gin.wait(last_gin_req);  // 等待该 peer 的最后一个请求
        }
    }
}

1.4 JIT 编译层

JIT 层在 csrc/kernels/elastic/engram.hpp 中，使用 CRTP 模式：

class EngramFetchRuntime final : public jit::LaunchRuntime<EngramFetchRuntime> {
    struct Args {
        // Templated arguments (编译期常量)
        int num_entries_per_rank, num_hidden_bytes, num_sf_packs;
        int num_entries_per_token, num_scaleout_ranks, num_scaleup_ranks;
        int64_t num_cpu_bytes_per_rank;
        int num_qps;
        bool allow_hybrid_mode;
        // ...
    };

    static std::string generate_impl(const Args& args) {
        // 根据 hybrid 模式选择不同的 team 和 peer 计算
        if (args.allow_hybrid_mode) {
            num_rdma_peers = args.num_scaleout_ranks;
            num_ranks_per_rdma_peer = args.num_scaleup_ranks;
            team_tag = "ncclTeamTagRail";     // scale-out 使用 rail team
        } else {
            num_rdma_peers = args.num_scaleout_ranks * args.num_scaleup_ranks;
            num_ranks_per_rdma_peer = 1;
            team_tag = "ncclTeamTagWorld";    // 全局 world team
        }
        // 生成模板实例化代码
        return fmt::format(R"(
            #include <deep_ep/impls/engram_fetch.cuh>
            static void __instantiate_kernel() {{
                auto ptr = reinterpret_cast<void*>(&{});
            }}
        )", func_name);
    }
};

JIT 设计要点：

  • QP 数量、hidden size、entries per token 等作为模板参数传入，编译器可针对性优化
  • Hybrid 模式 vs Direct 模式生成不同的 team_tag 和 peer 计算逻辑
  • 每个 kernel 使用 __launch_bounds__(kNumThreads, 1) 强制每 block 1 个线程块

2. 使用方式

2.1 Engram Write

engram_write 将本地 KV 数据写入对称内存的 CPU 端：

# 计算存储需求
num_gpu_bytes, num_cpu_bytes = deep_ep.ElasticBuffer.get_engram_storage_size_hint(
    num_entries=524288, hidden=128,
    num_max_tokens_per_rank=512, dtype=torch.bfloat16)

# 创建 buffer（CPU 段用于 Engram 存储）
buffer = deep_ep.ElasticBuffer(
    group,
    num_bytes=num_gpu_bytes + num_cpu_bytes,
    num_cpu_bytes=num_cpu_bytes,
    num_allocated_qps=num_qps,
    allow_hybrid_mode=True)

# 写入本地 KV 到 CPU 段
local_kv = torch.randn((num_entries, hidden), dtype=torch.bfloat16, device='cuda')
buffer.engram_write(local_kv)

注意：engram_write 内部调用 cudaMemcpyAsync 从 GPU tensor 拷贝到 CPU 段的对称内存区域。虽然源数据在 GPU 上，但目标是通过 CUDA Unified Memory 映射到 CPU 地址空间的物理内存，NIC 可以直接通过 RDMA 读取。

2.2 Engram Fetch

engram_fetch 发起远端查表：

# indices: [num_tokens, num_entries_per_token] 全局 entry 索引
indices = torch.randint(0, num_ranks * num_entries,
                        (num_tokens, num_entries_per_token), dtype=torch.int32)

# 发起 RDMA Get（非阻塞）
hook = buffer.engram_fetch(indices)

# ... 可在此插入计算 kernel 以 overlap ...

# 等待 RDMA 完成并获取数据
data, sf = hook()  # data: [num_tokens, num_entries_per_token * hidden]

延迟执行（deferred execution）模式允许用户在 issue 和 wait 之间插入计算 kernel，实现通信与计算的 overlap。

2.3 FP8 模式

Engram 支持 FP8 存储 + 全局复制的 scaling factor：

# FP8 模式：数据以 FP8 存储，SF 全局复制
local_fp8, local_sf = per_token_cast_to_fp8(local_bf16)

# SF 全局复制到所有 rank（all-gather）
sf = torch.empty((num_ranks * num_entries, num_sf_packs), ...)
dist.all_gather_into_tensor(sf, local_sf, group)

# 写入：FP8 数据走 RDMA，SF 本地查表
buffer.engram_write(local_fp8, sf=sf)

# 获取：FP8 数据通过 RDMA，SF 通过本地 gather
data, fetched_sf = buffer.engram_fetch(indices)()

设计智慧：FP8 scaling factor 不通过 RDMA 传输，而是在所有 rank 本地冗余存储。这样：

  • RDMA 只传输 FP8 数据（节省带宽）
  • SF 查表通过本地 memory read（延迟极低）
  • 避免 RDMA 传输小数据（SF 通常只有 4-16 bytes/entry）的 overhead

3. NCCL Gin 交互机制

3.1 Gin Handle 构造

每个 QP 对应一个 NCCL Gin handle：

const auto gin = handle::NCCLGin(nccl_dev_comm, nccl_window, qp_idx,
                                  NCCL_GIN_RESOURCE_SHARING_CTA);

参数含义：

  • nccl_dev_comm：NCCL 设备端 communicator
  • nccl_window：对称内存窗口（所有 rank 可访问的共享内存区域）
  • qp_idx：QP 索引（每个 block 一个 QP）
  • NCCL_GIN_RESOURCE_SHARING_CTA：资源分享模式（CTA = Cooperative Thread Array，即 block 内共享）

3.2 RDMA Get 原语

核心 RDMA 操作通过 gin.get 发起：

gin.get<team_t, ncclCoopThread, ncclGin_SegmentMixed>(
    math::advance_ptr(storage, src_byte_offset),  // 源地址（远端对称内存）
    math::advance_ptr(fetched, token_idx * kNumHiddenBytes),  // 目的地址（本地 GPU）
    kNumHiddenBytes,    // 传输字节数
    peer_idx,           // 目标 RDMA peer
    extra_options);     // 聚合选项

模板参数：

  • team_t：通信组类型（ncclTeamTagWorld 或 ncclTeamTagRail）
  • ncclCoopThread：协作线程模式（单线程发起，非 warp 协作）
  • ncclGin_SegmentMixed：混合段模式（源在 CPU 段，目的在 GPU 段）

3.3 Flush 与 Doorbell

RDMA 请求默认聚合（aggregate），达到一定数量后 flush：

// 每 kGinQPFlushDepth 个请求 flush 一次
(request_idx % kGinQPFlushDepth == (kGinQPFlushDepth - 1))
    ? 0   // flush（不聚合）
    : ncclGinOptFlagsAggregateRequests  // 聚合请求

// 最终 flush：ring doorbell 通知 NIC
gin.flush_async<team_t, ncclCoopThread>(i, request_ptr);

Flush 机制：ncclGinOptFlagsAggregateRequests 告诉 Gin 不要立即发送，而是将多个 get 请求聚合后一次性 flush。这减少了 doorbell ringing 次数，提高吞吐。flush_async 将最后一个请求的 handle 写入 last_gin_requests，供 wait kernel 使用。

4. RoCE 与 NVLink 路径处理

4.1 RoCE (RDMA) 路径

Engram 的远程访问完全基于 RDMA（RoCE 或 InfiniBand）：

// 路由计算：owner rank → RDMA peer
const auto peer_idx = owner_rank_idx / kNumRanksPerRDMAPeer;
const auto intra_peer_rank_idx = owner_rank_idx % kNumRanksPerRDMAPeer;

// 源地址在 CPU 段（对称内存）
const auto src_byte_offset = int64_t(intra_peer_rank_idx) * kIntraRankStorageStride
                           + int64_t(local_entry_idx) * kNumHiddenBytes;

// 发起 RDMA Get（跨节点）
gin.get<team_t, ncclCoopThread, ncclGin_SegmentMixed>(
    advance_ptr(storage, src_byte_offset),  // 远端 CPU 段
    advance_ptr(fetched, token_idx * kNumHiddenBytes),  // 本地 GPU
    kNumHiddenBytes, peer_idx, ...);

RoCE 路径特点：

  • 数据从远端节点的 CPU 物理内存（通过 CUDA Unified Memory 映射）直接读取
  • 经过 RDMA NIC（RoCE v2 或 IB）传输
  • 写入本地 GPU VRAM
  • 全程无需 CPU 参与（GPU-Initiated）

4.2 NVLink 路径

Engram 的 engram_fetch kernel 本身不直接处理 NVLink——它只发起 RDMA Get。但 DeepEP 的 barrier 机制区分了 NVLink 和 RDMA：

// comm.cuh: scaleup_barrier 根据拓扑选择路径
if constexpr (kIsScaleupNVLink) {
    // NVLink 路径：使用 LSA (Load-Store Atomic) 屏障
    nvlink_barrier_wo_local_sync<...>(gin, workspace, rank_idx, sm_idx, thread_idx);
} else {
    // RDMA 路径：使用 Gin signal 屏障
    gin_barrier_wo_local_sync<...>(gin.nccl_dev_comm, 1, rank_idx, sm_idx, thread_idx);
}

对于 Engram 的 NVLink 场景（同一节点内 GPU 访问另一 GPU 的 Engram 存储）：

  • 如果 scale-up 域使用 NVLink，engram_write 后的 barrier 使用 NVLink 原子操作
  • 但 engram_fetch 的 RDMA Get 仍然走 RDMA 路径（即使目标在同一节点）
  • 这是因为 Engram 的存储位于 CPU 段，GPU 间 NVLink 无法直接访问 CPU 内存

关键限制：Engram 的远程访问始终走 RDMA，即使目标 rank 在同一 NVLink 域内。这是因为 Engram 数据存储在 CPU 物理内存（对称内存的 CPU 段），而 NVLink 不支持 GPU 直接访问远端 CPU 内存。如果同一节点内 GPU 需要访问对方的 Engram 数据，仍然需要经过 RDMA loopback（RoCE/IB 回环）。

4.3 Hybrid 模式

Hybrid 模式（allow_hybrid_mode=True）改变了 RDMA peer 的路由方式：

if (args.allow_hybrid_mode) {
    // Hybrid: scale-out 每个 rail 一个 peer
    num_rdma_peers = args.num_scaleout_ranks;
    num_ranks_per_rdma_peer = args.num_scaleup_ranks;
    team_tag = "ncclTeamTagRail";  // 使用 rail team
} else {
    // Direct: 每个 rank 一个 peer
    num_rdma_peers = args.num_scaleout_ranks * args.num_scaleup_ranks;
    num_ranks_per_rdma_peer = 1;
    team_tag = "ncclTeamTagWorld";  // 使用 world team
}

Directscaleout × scaleup1ncclTeamTagWorld扁平拓扑
HybridscaleoutscaleupncclTeamTagRailNVLink + RDMA 两层

Hybrid 模式下，一个 RDMA peer 对应一个 scale-out 域（rail），该 rail 内的多个 scale-up rank 通过 NVLink 共享数据。这减少了跨节点 RDMA 的 QP 数量。

5. 查表并发机制

5.1 QP 并行化

Engram 的并发核心是 多 QP (Queue Pair) 并行：

// 每个 QP 对应一个 CUDA block
const auto qp_idx = blockIdx.x;

// 每个 QP 内有多个 warp 并行处理不同 token
const auto global_warp_idx = qp_idx * kNumWarps + warp_idx;

// 循环处理：每个 warp 处理 num_tokens * kNumEntriesPerToken / (kNumQPs * kNumWarps) 个 entry
for (int i = global_widx; i < num_tokens * kNumEntriesPerToken; i += kNumQPs * kNumWarps) {
    // 查表 + RDMA Get
}

并行度分析：

  • num_qps：默认 = GPU SM 数量（如 H100 = 132 SM），每个 SM 一个 QP
  • kNumWarps：每个 QP 内的 warp 数（1024 threads / 32 = 32 warps）
  • 总并行度：num_qps × 32 warps 同时发起 RDMA Get

5.2 路由分解

全局 entry index 被分解为 RDMA peer + 本地 entry：

const auto global_idx = __ldg(indices + i);           // 全局索引
const auto owner_rank_idx = global_idx / kNumEntriesPerRank;  // 所属 rank
const auto local_entry_idx = global_idx % kNumEntriesPerRank;  // rank 内偏移

// 路由到 RDMA peer
const auto peer_idx = owner_rank_idx / kNumRanksPerRDMAPeer;
const auto intra_peer_rank_idx = owner_rank_idx % kNumRanksPerRDMAPeer;

// 计算源地址
const auto src_byte_offset = int64_t(intra_peer_rank_idx) * kIntraRankStorageStride
                           + int64_t(local_entry_idx) * kNumHiddenBytes;

查表并发设计：每个 entry 的查表完全独立——通过 __ldg (load global 只读缓存) 读取 index，计算路由，发起 RDMA Get。不同 warp/QP 之间无数据依赖，天然支持最大并发。atomicAdd_block 仅用于统计每个 peer 的请求数以支持 flush 控制。

5.3 原子计数与 Flush 控制

__shared__ int num_requests_per_peer[kNumRDMAPeers];

// 原子计数：追踪每个 peer 的请求数
const auto request_idx = atomicAdd_block(num_requests_per_peer + peer_idx, 1);

// 每 kGinQPFlushDepth 个请求 flush 一次
issue_rdma_get(i, peer_idx, src_byte_offset,
    (request_idx % kGinQPFlushDepth == (kGinQPFlushDepth - 1))
        ? 0   // 不聚合 = flush
        : ncclGinOptFlagsAggregateRequests);

// 最终 flush：确保所有请求被提交
gin.flush_async<team_t, ncclCoopThread>(i, request_ptr);

Flush 策略：

  • 聚合请求减少 doorbell ringing 开销
  • 每 kGinQPFlushDepth 个请求强制 flush 一次，防止请求无限堆积
  • 最终无条件 flush 确保所有请求被 NIC 处理

6.2 CPU 段注册与跨进程映射

CPU 段的创建使用 CUDA Virtual Memory Management：

// 1. 创建 NUMA-local CPU 分配
static cpu_handle_t create_cpu_handle(int64_t num_cpu_bytes) {
    DeviceContext ctx;
    auto cpu_prop = ctx.cpu_alloc_prop();  // NUMA-local 属性

    CUmemGenericAllocationHandle handle;
    cumem_create_with_fallback(&handle, num_cpu_bytes, &cpu_prop);

    // 2. 导出为 POSIX FD（跨进程共享）
    int fd = -1;
    cuMemExportToShareableHandle(&fd, handle,
        CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR, 0);

    return {getpid(), fd};
}

// 3. 跨进程导入（通过 pidfd_open + pidfd_getfd）
int pidfd = syscall(SYS_pidfd_open, pid, 0);
int local_fd = syscall(SYS_pidfd_getfd, pidfd, fd, 0);
cuMemImportFromShareableHandle(&cpu_handles[i], (void*)(uintptr_t), local_fd, ...);

跨进程内存共享机制：每个 rank 创建自己的 CPU 段，通过 POSIX file descriptor 导出。其他 rank 通过 Linux pidfd API 获取 FD 并 import 到自己的 VA 空间。这允许 NIC 通过 RDMA 直接访问远端进程的 CPU 内存。

6.3 Engram 存储的对称内存语义

Engram 的"对称内存"含义：

  • 地址对称：每个 rank 的 CPU 段在各自 VA 空间中的偏移相同（num_gpu_buffer_bytes + rank_idx * num_cpu_buffer_bytes）
  • 内容不对称：每个 rank 的 CPU 段只存储自己的 local entries
  • 全局可寻址：通过 ncclWindow_t，任何 rank 可以计算远端 rank 的 CPU 段地址并发起 RDMA Get

Engram 的存储布局（CPU 段内）：

CPU segment for rank r:
┌────────────────────────────────────────────────────────┐
│ entry 0  │ entry 1  │ ...  │ entry (num_entries-1)     │
│ hidden*B │ hidden*B │      │ hidden*B                  │
└────────────────────────────────────────────────────────┘

// 全局视角（所有 rank 的 CPU 段拼接）:
┌──────────────┬──────────────┬─────┬──────────────┐
│ rank 0       │ rank 1       │ ... │ rank N-1     │
│ entries      │ entries      │     │ entries      │
└──────────────┴──────────────┴─────┴──────────────┘

7. HybridElasticSymmetricMemory 深度专题

专题核心问题：HybridElasticSymmetricMemory 为什么要设计成"对称"架构？这种对称性为 Engram 的 GPU 单向查表式内存访问带来什么本质好处？从 RoCE 相关代码、测试代码和初始化操作三个维度分析，对称内存到底能否跨越节点，还是仅限于节点内或 Engram 域内？

7.1 为什么要设计对称架构

"对称"的精确定义：在 DeepEP 中，"symmetric"不是指数据内容对称（各 rank 存储不同数据），而是指虚拟地址布局对称——每个 rank 的 NCCL Window 具有完全相同的 VA 结构：

// 所有 rank 的窗口布局完全相同（nccl.cu L140）
ncclCommWindowRegister(comm, raw_window_ptr, sym->num_bytes, &window, ...);

// 每个 rank 的 VA 布局:
┌─────────────────────────────────────────────────────────────────┐
│  [GPU VRAM (num_gpu_bytes)]  │  CPU Segments (num_cpu_bytes)   │
│  所有 rank 大小相同          │  所有 rank 大小相同              │
└─────────────────────────────────────────────────────────────────┘

对称架构的核心好处：O(1) 全局地址计算。

关键洞察：因为所有 rank 的窗口布局对称，任意 rank 可以在本地计算出任意其他 rank 的存储偏移量，无需查询、无需通信、无需地址转换：

// engram_fetch.cuh L57-66 — 本地计算远端地址
const auto owner_rank_idx = global_idx / kNumEntriesPerRank;
const auto local_entry_idx = global_idx % kNumEntriesPerRank;
const auto peer_idx = owner_rank_idx / kNumRanksPerRDMAPeer;
const auto intra_peer_rank_idx = owner_rank_idx % kNumRanksPerRDMAPeer;
const auto src_byte_offset = int64_t(intra_peer_rank_idx) * kIntraRankStorageStride
                           + int64_t(local_entry_idx) * kNumHiddenBytes;

这个偏移量在任何 rank 上计算结果都相同——对称性保证了偏移量的全局一致性。

对比非对称方案：

方案地址计算开销RDMA 友好
非对称（各 rank 布局不同）需要查询远端布局信息O(通信) 或 O(查表)否
对称（DeepEP 采用）本地 O(1) 计算零是
全局统一 VA（CXL 风格）直接指针访问需要硬件支持部分

7.2 对称性对 Engram 单向查表的意义

Engram 的 GPU 单向内存访问（GPU 主动读远端，远端 GPU 不参与）依赖对称性实现三个关键能力：

7.2.1 无状态路由

GPU kernel 计算出的 src_byte_offset 直接传递给 NCCL Gin：

gin.get<team_t, ncclCoopThread, ncclGin_SegmentMixed>(
    math::advance_ptr(storage, src_byte_offset),  // 本地 VA 计算的偏移
    math::advance_ptr(fetched, token_idx * kNumHiddenBytes),  // 本地 GPU 目的
    kNumHiddenBytes, peer_idx, ...);




关键机制：gin.get 内部将 src_ptr 转换为窗口偏移（src_ptr - lsa_base_ptr），然后告诉 NIC："从 peer_idx 的窗口偏移 XX 处读取数据"。因为所有 peer 的窗口布局对称，本地计算的偏移量在远端同样有效。





7.2.2 单向性（One-Sided）保证



远端 GPU 完全不参与数据传输：



Node A (发起端)                    Node B (远端)
┌─────────────────┐                ┌─────────────────┐
│ GPU Kernel      │                │ GPU 空闲        │
│ 计算 src_offset │                │ (不参与)        │
│     ↓           │                │                 │
│ NIC (A)         │══ RDMA Get ═══▶│ NIC (B)         │
│                 │                │ 从本地 CPU 段   │
│                 │                │ 读取物理内存    │
│     ↓           │                │                 │
│ GPU VRAM (A)    │◀═══════════════│                 │
└─────────────────┘                └─────────────────┘



对称性使得这种单向操作成为可能——发起端不需要远端的任何信息（地址、状态、同步），仅凭全局索引即可定位数据。



7.2.3 对称性消除了 CPU 查表需求



在传统 RDMA 编程中，CPU 需要维护地址翻译表（MR 查找、lkey/rkey 管理）。对称架构下：



    

  • 偏移量 = 地址（无需 MR 查找）
    • 

  • 窗口基址 = 常量（lsa_base_ptr）
    • 

  • 远端 key = 隐式（peer_idx → NCCL 内部管理 rkey）
    •

8. SM 如何调用 RoCE 能力



7.1 "0 SM" 的本质



Engram 被称为"0 SM"通信，但这需要精确理解：





"0 SM" 的准确含义：Engram 的 RDMA Get 操作不长期占用 SM。kernel 启动后，SM 只执行少量指令（计算地址、发起 RDMA doorbell），然后 kernel 结束。RDMA 数据传输由 NIC 异步完成，无需 SM 参与。这与传统通信 kernel（如 NCCL）需要 SM 持续参与数据搬运完全不同。





7.2 NCCL Gin GPU-Initiated API



SM 通过 NCCL Gin 的 GPU 端 API 直接操作 RDMA：



// 1. 构造 Gin handle（绑定到特定 QP）
const auto gin = handle::NCCLGin(nccl_dev_comm, nccl_window, qp_idx,
                                  NCCL_GIN_RESOURCE_SHARING_CTA);

// 2. 发起 RDMA Get（GPU 指令，直接写 NIC doorbell）
gin.get<team_t, ncclCoopThread, ncclGin_SegmentMixed>(
    src_ptr, dst_ptr, size, peer_idx, options);

// 3. Flush（ring doorbell）
gin.flush_async<team_t, ncclCoopThread>(peer_idx, request_ptr);

// 4. Wait（轮询 completion）
gin.wait(last_gin_req);



这些 API 在 GPU kernel 内执行，直接操作 NIC 的 doorbell register，绕过 CPU 和 NIC driver。



7.3 实际 SM 占用分析



虽然称为"0 SM"，但实际仍有短暂占用：





阶段SM 占用持续时间说明


engram_fetch kernelnum_qps 个 block~μs 级计算地址 + 发起 RDMA


engram_fetch_wait kernelnum_qps 个 block等待 RDMA 完成轮询 completion


数据传输0 SM取决于数据量NIC DMA 异步完成







实际占用：engram_fetch kernel 使用 __launch_bounds__(1024, 1)，每个 QP 一个 block（1024 threads）。对于 H100（132 SM），如果 num_qps=132，则短暂占用全部 SM，但 kernel 执行时间极短（微秒级）。wait kernel 类似。真正的数据传输期间 SM 完全空闲。

  • 无需跨进程通信，直接函数调用
    • 




8.2 ElasticBuffer 生命周期




初始化:
  1. 创建 NCCL communicator (ProcessGroup)
  2. 计算 buffer 大小 (GPU + CPU)
  3. 创建 HybridElasticSymmetricMemory
     - Reserve VA space
     - Map GPU segment (front)
     - Import + map CPU segments from all scale-up ranks
  4. 初始化 workspace (barrier 等)

使用:
  - engram_write(): GPU tensor → CPU 段 (cudaMemcpyAsync)
  - engram_fetch(): 发起 RDMA Get → 返回 hook
  - hook(): 等待 RDMA 完成 → 返回数据

销毁:
  - barrier() 确保所有操作完成
  - 释放 host workspace
  - 销毁 NCCL symmetric memory context
  - Unmap + release GPU/CPU segments
  - Free VA space



8.3 独立部署可行性分析



Engram 能否作为独立服务部署（类似 KV Cache 池化）？





部署模式当前状态可行性挑战


与模型共部署✅ 当前实现完全支持无


独立进程（同 GPU）❌ 未实现可行但复杂需要 IPC 机制传递 indices


独立 GPU（分离式）❌ 未实现理论上可行需要独立 NCCL group


CPU-only 节点❌ 不支持需要重新设计Engram 需要 GPU 发起 RDMA







独立部署的关键障碍：


    

  1. NCCL Communicator 绑定：Engram 依赖 NCCL communicator 管理对称内存窗口，独立部署需要独立的 NCCL group
    2. 

  2. 地址空间隔离：engram_fetch 直接在 GPU kernel 内计算远端地址，独立进程需要跨进程 VA 映射
    3. 

  3. 同步机制：当前使用 dist.barrier() 进行 CPU 同步，独立部署需要替代同步方案
    4. 

  4. 内存注册：CPU 段的跨进程共享依赖 POSIX FD + pidfd，独立部署需要额外的服务发现机制
    5.

11. 总结与设计洞察



核心设计原则



    

  1. GPU-Initiated Everything：从地址计算到 RDMA doorbell，全部在 GPU kernel 内完成，消除 CPU 瓶颈
    2. 

  2. 对称内存抽象：通过 CUDA Virtual Memory Management 将远端 CPU 内存映射到本地 VA，实现位置透明的查表
    3. 

  3. QP 并行化：每个 SM 一个 QP，warp 级协作，最大化 RDMA 并发
    4. 

  4. 延迟执行：fetch 返回 callable，支持通信-计算 overlap
    5. 

  5. FP8 优化：数据走 RDMA，scaling factor 本地冗余，避免小数据传输
    6.

局限与展望



    

  • 只支持 read：当前 Engram 只支持远程读取（Get），不支持远程写入
    • 

  • CPU 段依赖：Engram 存储必须在 CPU 物理内存，无法直接存储在远端 GPU VRAM
    • 

  • RDMA 路径唯一：即使目标在同一 NVLink 域，仍然走 RDMA（无法利用 NVLink 的 GPU-to-GPU 带宽）
    • 

  • 实验性质：API 标记为 Experimental，接口可能变化
    • 

  • 未来方向：支持 GPU VRAM 直接注册（绕过 CPU 段）、支持 write 原语、与 Disaggregated Inference 框架集成
    •
