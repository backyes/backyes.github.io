Thesis

URPC（Unified Remote Procedure Call）是灵衢（Lingqu）内存语义开发包 UMDK 的核心组件之一，它在 UB 总线提供的原始内存语义（URMA）之上，构建了一套完整的远程过程调用协议栈。URPC 并非简单地在 RDMA 动词层封装一层 RPC，而是在 传输模式抽象、流控与内存管理、协议状态机、安全加密 和 多场景传输加速 五个维度上做了系统性的增量创新。

URPC 的设计哲学：UB 提供的是"内存语义原语"（register/unregister/import/read/write/atomic），URPC 在此之上构建的是"函数调用语义"——包括请求-响应协议、参数引用传递、流控窗口、保活探测和多模态传输。这不是 transport 的简单封装，而是一个完整的 protocol stack。

关键调用链（CodeGraph 验证）

以下是通过 CodeGraph 验证的 4 条核心调用链，展示了从用户 API 到硬件操作的完整路径：

Call Chain 1: 函数调用（Client 发送 REQ）

urpc_func_call() → channel_get() → urpc_get_local_queue()（RR 选择） → req_entry_get()（分配请求条目） → urpc_req_fill_basic_info()（填充 REQ 头） → l_queue->ops->send() → send_recv_send() → urma_post_jetty_send_wr()

Call Chain 2: 函数执行（Server 接收 REQ）

urma_poll_jfc()（JFR 完成事件） → send_recv_poll_rx() → process_rx_cr() → urpc_func_exec() → sync_handler()/async_handler()（用户函数） → urpc_func_return() → l_queue->ops->send()（发送 RSP）

Call Chain 3: UMQ 数据发送

umq_enqueue() → umq_tp_enqueue() → umq_ub_enqueue_impl() → umq_ub_fill_wr_impl()（填充 SGE + 流控窗口检查） → umq_ub_post_impl() → urma_post_jetty_send_wr()

Call Chain 4: 初始化流程（CodeGraph 验证）

// dp.c:352-533
uint64_t urpc_func_call(uint32_t chid, urpc_call_wr_t *wr, urpc_call_option_t *option) {
    // 1. 获取 channel（读锁保护）
    channel = channel_get(chid);

    // 2. 选择 local queue（round-robin）
    l_queue = urpc_get_local_queue(channel, option);
    //    └─ channel_get_next_local_queue() → RR 轮转

    // 3. 选择 remote queue（round-robin）
    r_queue = urpc_get_remote_queue(channel, option);

    // 4. 分配 tx_ctx（从 queue 的 slab allocator）
    ctx = queue_ctx_get(l_queue, QUEUE_CTX_TYPE_TX);

    // 5. 分配 req_entry（hash 表 + 线性探测）
    req_entry = req_entry_get(channel, ctx);
    //    └─ req_id = channel->req_id++ & (size-1)
    //    └─ while (req_entry->valid) { req_id++; linear_probe }

    // 6. 填充 REQ 协议头
    req_head = (urpc_req_head_t *)wr->args[0].addr;
    urpc_req_fill_basic_info(req_head, ack, channel_id);
    urpc_req_fill_req_info_without_dma(req_head, func_id, len, req_id, func_defined);

    // 7. 可选加密（keepalive 或 ext_ops->encrypt）
    func_call_sge_encrypt(func_defined, channel, r_queue, req_entry, wr);

    // 8. 填充 tx_ctx
    fill_req_tx_ctx(ctx, chid, l_qh, req_id, wr, option);

    // 9. 启动超时定时器（如果配置了 timeout）
    timeout_create(option, req_entry, func_defined, wr);

    // 10. 发送（调用 queue ops → send_recv_send → urma_post）
    l_queue->ops->send(l_queue, &queue_wr);

    return req_id;  // 返回请求句柄
}

tx_ctx 生命周期（双次释放机制）

URPC 使用 tx_ctx_try_put() 实现双次释放：tx_ctx 必须经历两个"完成事件"才能被释放回 slab：

// dp.c:650-658
void tx_ctx_try_put(tx_ctx_t *ctx) {
    if (ctx->free_events_completed == FALSE) {
        ctx->free_events_completed = TRUE;  // 第一次：TX CQE
        return;
    }
    queue_ctx_put(QUEUE_CTX_TYPE_TX, ctx);  // 第二次：ACK/RSP → 真正释放
}

这解决了 TX CQE 和 ACK/RSP 并发到达时的竞态条件——无论哪个先到，都必须等两个都完成。

    // 1. 解析 immediate 中的元数据
    uint16_t buf_num = imm.ub_plus.msg_num;    // 批处理 buf 数量
    uint16_t msg_id = imm.ub_plus.msg_id;      // 消息 ID（用于去重）

    //    └─ umq_buf_alloc(total_size, 1, ...) 从 huge pool 分配

    // 4. 逐块发起 READ
    for (uint32_t i = 0; i < buf_num; i++) {
        src_sge[i].addr = ref_sge[i].addr;           // 远端地址
        src_sge[i].tseg = imported_tseg_list[ref_sge[i].mempool_id];
        dst_sge[i].addr = tmp_buf->buf_data;          // 本地地址
        dst_sge[i].tseg = tseg_list[tmp_buf->mempool_id];
        urma_post_jetty_send_wr(queue->jetty, &urma_wr, &bad_wr); // READ
    }

    // 5. 完成后发送 REVERSE_PULL_MEM_DONE 确认
    //    └─ umq_ub_write_imm(imm = REVERSE_PULL_MEM_DONE)
}

Conclusion

URPC 在 UB 总线上构建了一套完整的"从硬件原语到函数调用语义"的技术栈。通过本次深度代码分析，我们揭示了以下关键洞察：

  • 分层抽象：URMA → UMQ/URPC Framework → 公共 API，每层只关注本层职责，通过 ops 接口实现多态
  • 带内控制：利用 immediate 数据编码流控、内存导入、反向拉取等控制协议，不占用数据通道
  • 并发安全：tx_ctx 双次释放、req_entry hash+线性探测、读写锁分离等精细并发控制
  • 用户可选：每一层增量功能都是可选的（feature flag），适应不同场景
  • 生产级特性：Keepalive、DFX、SSL/TLS、300K 并发 Channel

从架构视角看，URPC 的设计遵循了"分层抽象、带内控制、用户可选"的原则——既能以最小开销运行在延迟敏感的推理场景，也能以全功能模式运行在需要流控和加密的训练/存储场景。
