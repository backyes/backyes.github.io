1 为什么 AI 超节点需要统一编址？

很多人在讨论统一编址时，都会从 CUDA Unified Virtual Address（UVA）或者 CPU Virtual Memory 开始介绍。但对于 AI 超节点来说，这其实已经偏离了问题本身。

核心观点：真正推动统一编址发展的，不是虚拟内存，而是 AI Workload 的变化。

1.1 从独立计算-通信到融合算子

过去 GPU Kernel 更多是访问本地 HBM，GPU 之间的通信由 NCCL、MPI 等通信库完成，一次计算和一次通信是两个相互独立的阶段。

但是今天越来越多的 AI 算法开始采用融合算子（Fusion Operator）的设计：

  • MoE Fusion Kernel：执行过程中直接访问不同 Expert 所在 GPU 的参数
  • Cross-GPU Attention：直接读取远端 GPU 上的 KV Cache
  • Embedding Cache / Engram Memory：动态图存储等工作负载，要求 GPU 在 Kernel 内部执行大量随机远程访问

也就是说，通信已经开始融合进计算本身。

1.2 融合算子对编址的诉求

对于一个融合算子而言，它真正希望表达的是：

// 理想语义：位置透明的远端访问 float val = load(ptr);

而不是：

// 显式指定位置：破坏了计算语义 float val = load(gpu7, hbm2, offset);

更不希望整个访问过程退化成：

Fusion Kernel │ Suspend │ CPU Runtime │ Address Lookup │ Network │ Resume Kernel

因为这意味着 GPU 必须退出执行流，由 CPU 或 Runtime 完成地址解析，再重新发起访问。这不仅增加软件路径延迟，更重要的是破坏 GPU 的流水线，使远程 Memory Load 无法像本地 Load 一样连续发射。

1.3 第一性原理：Location Transparency

因此，从第一性原理来看，统一编址真正解决的问题不是"统一地址"，而是：

让 GPU 能够像访问本地 HBM 一样访问远端 Memory。

换句话说，它真正提供的是：Location Transparency（位置透明）。

Kernel 不应该关心：

  • 数据在哪张 GPU
  • 属于哪个 HBM Stack
  • 是否经过几个 NVSwitch
  • 是否属于哪个 OS Domain
  • 是否因为迁移已经换了一张 GPU

这些都应该由底层系统负责。

1.4 Location Service 模型

因此，一个统一编址系统，本质上是在 GPU 和 Memory 之间增加了一层 Location Service：

AI Object │ Location Service │ Physical Location │ Transport │ Remote Memory

这里实际上对应三个彼此独立的问题：

问题职责Hopper 对应
Location对象在哪里？Control Fabric
Translation逻辑地址 → 可访问位置Memory Fabric
Transport如何把请求送过去？Transport Fabric

这三个问题，也恰好对应 Hopper 后面的三个 Fabric。

2 Hopper 是如何实现统一编址的？

理解第一性原理以后，再来看 Hopper，就会发现 NVIDIA 并没有把统一编址放到 NVLink，而是把整个系统划分成三个职责完全不同的层次。

CUDA Runtime │ ────────────────────────────────────── Control Fabric ────────────────────────────────────── Fabric Manager / NVLSM / Driver ────────────────────────────────────── Memory Fabric ────────────────────────────────────── GMMU / TLB / Page Table / Memory Aperture / Peer Mapping ────────────────────────────────────── Transport Fabric ────────────────────────────────────── NVLink / NVSwitch / HBM

2.1 Control Fabric：管理整个 GPU Fabric

Control Fabric 管理整个 GPU Fabric，包括 GPU Discovery、Topology Discovery、Partition、Routing Programming、Peer Registration 等。Fabric Manager 和 NVLSM 维护的是整个 NVL72 的资源拓扑，它们知道 GPU 在哪里、Switch 如何连接、路由如何建立，但它们并不知道 Tensor、KV Cache 或 Expert 等 AI 对象。

2.2 Memory Fabric：建立内存语义

Memory Fabric 负责建立内存语义。当 GPU Kernel 执行 load(ptr) 时，请求进入 GMMU，通过 TLB 和 Page Table 找到对应的 Page Table Entry。PTE 中已经记录了目标 Peer GPU 和 HBM Offset，Memory Aperture 只是消费这些映射关系，并不会主动查询 Fabric Manager。

也就是说，Memory Fabric 本身没有控制逻辑，它只是 Control Fabric 在 GPU 上留下的执行结果。

2.3 Transport Fabric：纯粹的数据平面

Transport Fabric 才是真正的数据平面。NVLink 和 NVSwitch 看到的只是 (Destination GPU, HBM Offset, Payload)，它们并不知道 Virtual Address，更不知道访问的是 Tensor、KV Cache 还是 Expert 参数。

关键洞察：NVLink 的职责始终是 Transport，而不是 Address Translation。

2.4 完整数据路径

Control Fabric │ 建立 Peer Mapping │ Memory Fabric (GMMU / Aperture) │ 解析目标 GPU │ Transport Fabric (NVLink)

3 Hopper Server 与 NVL72：统一编址在两个尺度上的区别

这里需要区分 Hopper Server 和 NVL72，因为两者的设计目标完全不同。

3.1 Hopper HGX Server（8 GPU）

在一台 Hopper HGX 服务器中，通常只有 8 张 GPU。Control Fabric 的管理范围局限于单机，Fabric Manager 和 CUDA Driver 完成 Peer Registration 后，就可以建立覆盖整个服务器的统一地址空间。

由于 GPU 数量有限，Peer Mapping、TLB 和 Page Table 的规模都比较容易控制，因此一次性建立 Global Address Space 是一种非常合理的选择。

3.2 NVL72（机柜级 GPU Fabric）

但 NVL72 已经不再是一台服务器，而是一个 GPU Fabric。Control Fabric 需要管理整个机柜的 GPU、NVSwitch、多级拓扑、多个 OS Domain、Partition、故障恢复等系统级资源，因此 NVIDIA 引入了独立的 Fabric Manager 和 NVLSM。

重要区分：Fabric Manager 和 NVLSM 维护的是整个机柜的 Fabric 资源，而不是内存页。

随后 CUDA Driver 根据这些拓扑信息，在每张 GPU 的 GMMU 中建立覆盖整个 NVL72 的 Peer Mapping。

3.3 两种尺度的编址体系

维度Hopper Server (8 GPU)NVL72 (72+ GPU)
Control Scope单机机柜
Control PlaneCUDA DriverFabric Manager + NVLSM
Memory Fabric单机 Global Address机柜 Global Address
Peer Mapping8 个 Peer72+ 个 Peer
TLB 压力低高
Partition不支持支持（MIG / Multi-tenant）

因此 Hopper/NVL72 实际采用的是：

Global Fabric │ Global Memory Fabric │ Global Address Space

Control Fabric 的作用域就是整个 NVL72，Memory Fabric 的作用域也覆盖整个 NVL72，两者保持一致。

4 为什么 Hopper 采用全局编址？

这一设计其实来自 HPC 的基本假设。

HPC 假设：传统 HPC 中，任何 MPI Rank 都可能与任何 Rank 通信，因此最简单的软件模型就是一次性建立整个 Fabric 的 Global Address Space。

Kernel 永远面对统一 Pointer，运行过程中不需要修改 Page Table，也不需要重新建立 Peer Mapping。

这是一种典型的用初始化成本换运行时效率的设计。对于几十张 GPU 的静态集群，这种方式非常合理。

5 AI Workload 改变了这一假设：统一编址真正需要的是什么？

AI 工作负载已经不再遵循"所有 GPU 都可能通信"的假设。

5.1 Communication Domain

一个 Attention Kernel 可能只涉及 GPU4~GPU7，一个 MoE Kernel 可能只访问几个 Expert 所在 GPU，一个推理实例甚至只使用 NVL72 中的一小部分 GPU。AI 的基本通信单位已经从整个 Fabric 变成了 Communication Domain。

5.2 类比 RDMA 的建立过程

这里可以借助 RDMA 的建立过程理解统一编址。

RDMA 并不是天然拥有远端地址。一次 RDMA Read 能够直接执行，前提是控制平面已经完成了 Memory Region 注册、Queue Pair 建立以及地址和权限交换。数据面能够做到零 CPU 参与，并不是因为地址天然存在，而是因为地址透明化工作已经提前完成。

NVLink 的统一编址其实也是同样的思想。GPU 能够直接执行 load(ptr)，不是因为 NVLink 天然知道远端地址，而是因为系统已经提前建立好了 Address Resolution Service，把逻辑地址转换成了 (Destination GPU, HBM Offset)。

5.3 真正必要的是什么？

因此，真正必要的不是一个覆盖整个 NVL72 的 Global Address Space，而是：

在开始通信之前，为当前计算任务建立地址透明化能力。

Global Address Space 只是实现 Address Transparency 的一种方式，而且是一种比较"奢侈"的方式。它要求整个 NVL72 在系统启动时维护覆盖所有 GPU 的 Peer Mapping，并依赖 Fabric Manager 等机柜级控制服务持续维护这一全局视图。

5.4 地址透明化的多种建立时机

理论上，地址透明化可以在很多不同的时刻建立：

建立时机作用域适用场景Hopper 支持
系统启动时整个 NVL72HPC 全对全通信✓（当前方案）
NCCL 初始化Communicator集合通信部分支持
推理实例启动实例级 Address Domain推理服务✗
融合算子启动Communication DomainMoE Fusion✗
第一性原理结论：真正不可缺少的是 Address Resolution Service，而不是 Global Address Space。什么时候建立地址透明化、建立多大的作用域、由谁维护，都是系统设计可以自由权衡的问题。

6 Hopper 今天的局限

从这个角度再来看 Hopper，就会发现它真正的限制并不在 NVLink，也不在 NVSwitch，而是在 Memory Fabric 的作用域。

今天，Control Fabric 管理整个 NVL72，因此 Memory Fabric 也覆盖整个 NVL72。即使一个 Fusion Kernel 只访问 4 张 GPU，每张 GPU 的 GMMU 仍然维护整个机柜的 Peer Mapping。

核心矛盾：Fabric Scope 与 Address Scope 被绑定在了一起。

随着未来 GPU 数量继续增加，这种绑定关系将带来越来越高的 Page Table、TLB、Peer Mapping 和生命周期管理成本，而这些成本与实际通信域并不匹配。

具体成本分析

成本项当前状态问题
Page Table覆盖整个 NVL72与实际通信域不匹配
TLB Miss全局映射导致 TLB 压力大远程访问延迟增加
Peer Mapping系统启动时一次性建立无法按需释放
Fabric Manager维护全局视图扩展性瓶颈

7 Next：Memory Fabric 从静态资源走向动态服务

未来并不需要推翻 Hopper 的三层架构。Control Fabric、Memory Fabric、Transport Fabric 的职责划分仍然是合理的，真正需要变化的是 Memory Fabric 的生命周期。

7.1 动态 Address Resolution Service

未来，Control Fabric 仍然负责 Discovery、Routing 和资源管理；Transport Fabric 仍然负责高带宽数据传输；而 Memory Fabric 则不再是系统启动时一次性建立的静态资源，而是 Runtime 根据 Communication Domain 动态构建的运行时服务。

Communication Domain │ ▼ Address Resolution Service (Control Plane) │ ▼ Address Domain (Page Table / Peer Mapping) │ ▼ Memory Fabric (GPU 可直接 load/store) │ ▼ Transport Fabric (NVLink / UALink / UB)

这里真正动态的是 Address Resolution Service。Memory Fabric 只是这些地址解析关系在 GPU GMMU 和页表中的具体体现。

7.2 从 VA 到 AI Object

进一步看，这一思路还可以继续演进。今天 Address Resolution Service 管理的是 Virtual Address → GPU + HBM Offset；未来完全可能提升到 AI Object → GPU + HBM Offset，围绕 KV Block、Expert、Embedding、Tensor Chunk 等 AI 对象建立对象级目录服务（Object Directory Service）。

演进阶段编址对象映射关系服务对象
CPU 时代Virtual PageVA → PA进程
Hopper 时代Virtual AddressVA → GPU + HBM Offset整个 Fabric
AI Native 时代Communication DomainDomain → Address Domain计算任务
未来AI ObjectObject → LocationFusion Kernel

届时，统一编址将不再只是内存管理机制，而会成为 AI Native Memory Fabric 的核心基础设施。

8 总结：统一编址不是统一地址，而是统一位置

🏛️ 核心定义

经过整个讨论，统一编址可以重新定义为：


"统一编址并不是构建一个覆盖整个超节点的统一地址空间，而是为当前计算任务建立位置透明的访问语义，使 GPU 能够像访问本地 HBM 一样访问远端内存。"


Hopper 选择在 系统启动阶段 建立覆盖整个 NVL72 的 Global Memory Fabric，这是面向 HPC 工作负载的一种优秀工程实现；但它并不是唯一实现。


对于未来 AI Native Supernode，更合理的方向可能是在 Runtime 驱动下，根据 Communication Domain 动态建立 Address Resolution Service 和 Address Domain，将统一编址从"静态的机柜级资源"演进为"按需构建的运行时能力"。

三个核心结论

结论 1：统一编址的第一性原理是 Location Transparency，不是 Unified Address。目标是让 GPU Kernel 用 load(ptr) 表达远端访问，而不是 load(gpu, hbm, offset)。
结论 2：Hopper 的三层 Fabric 架构（Control / Memory / Transport）是合理的，但 Fabric Scope 与 Address Scope 的绑定 是历史遗留问题，不是最优解。
结论 3：真正不可缺少的是 Address Resolution Service，不是 Global Address Space。建立时机、作用域、维护者都是可自由权衡的设计参数。

附录：DeepEP 编址设计的实证对照

前述第一性原理框架可以通过 DeepEP（DeepSeek 开源 EP 通信库）的编址设计得到实证。DeepEP 的 NVLink 域内 / RDMA 域外 / Hybrid 三种模式，恰好对应了统一编址理论的三种路径选择。

A.1 DeepEP 的三种编址模式

模式编址方式对应第一性原理Location Service
Normal (NVLink)Symmetric Pointer (LSA)域内统一编址ncclGetLsaPointer
Low-Latency (RDMA)Window + Offset域外注册内存ncclCommWindowRegister
Hybrid分层 (Rail + LSA)拓扑感知路径选择team 抽象屏蔽差异

A.2 DeepEP 对"动态编址"的探索

DeepEP 的 get_sym_ptr 返回值判断机制，本质上是一种运行时拓扑感知的路径选择：

// DeepEP dispatch.cuh:371-378 — 运行时路径选择 const auto dst_ptr = gin.get_sym_ptr<team_t>(recv_buffer..., dst_rank); if (dst_ptr != nullptr) ptx::tma_store_1d(dst_ptr, ...); // NVLink fast path (统一编址) if (dst_ptr == nullptr) gin.put<team_t>(..., dst_rank); // RDMA fallback (显式传输)

这恰好印证了第一性原理的结论：统一编址是 fast path，不是 only path。当 Location Service 能提供地址透明时，走 TMA 直写；不能时，fallback 到 RDMA 显式传输。

A.3 DeepEP 的"Address Resolution Service"雏形

DeepEP 的 NCCL Window 注册 + ncclGetLsaPointer 查询，本质上就是一个轻量级的 Address Resolution Service：

  • 注册阶段：ncclCommWindowRegister 将 buffer 注册到 NCCL 的地址空间
  • 查询阶段：get_sym_ptr 运行时查询目标 rank 是否可对称访问
  • 传输阶段：根据查询结果选择 TMA 或 RDMA
DeepEP 对理论的启示：DeepEP 的 Hybrid 模式（Scaleout warps RDMA + Forward warps NVLink 转发 + 并行 barrier）是"动态 Address Resolution Service"的一种工程实现——它不是系统启动时建立全局编址，而是每次 dispatch 时动态选择最优路径。这正是第一性原理所预言的"按需构建的运行时能力"。
