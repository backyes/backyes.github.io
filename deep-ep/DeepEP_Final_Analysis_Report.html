0. 执行摘要

DeepEP（DeepEveryParallel）是 DeepSeek 团队开发的 高性能 Expert Parallelism 通信库，核心目标是在 MoE（Mixture-of-Experts）模型训练和推理中实现 高吞吐、低延迟的 all-to-all GPU 通信。V2 版本相比 V1 实现了 1.3x 峰值性能提升，同时节省最多 4x SM 资源占用（从 24 SM 降至 4-6 SM）。

核心发现（三视角共识）
  • Token 重组不可避免：MoE routing 的随机性决定了接收端必须将乱序 token 重排为 expert-contiguous 布局
  • Dispatch 随机访存是数学必然：每个 token 独立选择 expert，目标地址不可预测，预取准确率仅 ~0.4%
  • Combine 可顺序执行：利用 dispatch 保存的 metadata，combine 可逆序还原
  • 层次化带宽利用：NVLink（~726 GB/s）vs RDMA（~90 GB/s）的 ~8x 差距决定了 scale-up/scale-out 分层
  • SM 最小化：通过 TMA 硬件卸载 + warp 特化，将通信占用从 24 SM 降至 4-6 SM

一、第一性原理分析（三视角综合）

通过架构、代码、理论三个独立视角的交叉验证，我们提炼出以下核心设计原理：

原理一：MoE Routing 的随机性本质 理论

MoE 模型的核心是 条件计算（Conditional Computation）：每个 token 通过 Gate 网络独立选择 Top-K 个 expert。设 token 数为 $T$，expert 数为 $E$，top-k 为 $K$，则 routing 矩阵 $R \in \{0,1\}^{T \times E}$ 的熵为：

$$H(R) = T \cdot K \cdot \log_2(E/K) \quad \text{bits}$$

对于 DeepSeek-V3 配置（T=8192, E=256, K=8），每次 forward pass 的 routing 熵约为 2.6 MB 的不可压缩随机信息。这意味着：

  • 目标 expert 的分布在统计上不可预测
  • 任何预取策略的准确率上限为 $K/E = 3.1\%$
  • 接收端必须为任意 token 分布做好准备

原理二：All-to-All 通信的 O(TopK) 放大效应 架构

在 EP（Expert Parallelism）中，每个 token 可能被路由到任意 rank，导致通信量放大：

$$\text{通信量} = T \times K \times \text{hidden\_size} \times \text{dtype\_size}$$ 对于 V3 配置（8K tokens, top-8, 7168 hidden, BF16）: $$= 8192 \times 8 \times 7168 \times 2 = 939.5 \text{ MB per layer}$$

这解释了为什么 EP 通信是 MoE 训练的瓶颈——通信量与 top-k 成正比，且每个 token 的目标 rank 不可预测。

原理三：NVLink/RDMA 层级带宽比决定拓扑分层 架构 硬件

互联类型带宽 (GB/s)延迟设计含义
NVLink (SM100)~726~1 μsscaleup 域内全带宽通信
RDMA (CX7)~90~5 μsscaleout 域间带宽受限
NVLink/RDMA 比~8x~5x层次化通信的动机

DeepEP 的 Hybrid mode 正是利用这一差距：scaleup 域内使用 NVLink 全带宽，scaleout 域间使用 RDMA，通过层次化 all-to-all 最小化跨域流量。

原理四：Token 重组的必然性——从随机到顺序的布局转换 三视角共识

这是三个 agent 从不同角度共同证明的核心原理：

共识：Token 重组不是设计选择，而是 MoE 计算的数学必然。
  • 理论视角：GEMM 要求输入矩阵在内存中连续排列。接收到的 token 按到达顺序排列（随机），而 expert 计算需要按 expert ID 排序（顺序）。这是一个 permutation 操作。
  • 架构视角：Expand mode 以 K 倍内存为代价，将 sparse-to-dense 转换提前到 dispatch 阶段，使下游 GEMM 可直接使用。
  • 代码视角：dispatch.cuh 的 atomicAdd slot allocation（L344-350）实现了 write-time reorganization，而 dispatch_copy_epilogue.cuh 实现了 copy-time reorganization。

原理五：Combine 的顺序访问特性 三视角共识

与 Dispatch 的随机访存不同，Combine 阶段可以顺序遍历接收到的 token：

// combine.cuh L86-93: 顺序遍历 token
for (int i = token_start_idx; i < token_end_idx; ++ i) {
    const int src_token_idx = __ldg(src_metadata + i * kMetadataStride) % kNumMaxTokensPerRank;
    const int src_rank_topk_idx = __ldg(src_metadata + i * kMetadataStride + 1);
    ...
}

这是因为 dispatch 阶段已将 routing 信息保存在 recv_src_metadata 中，combine 只需逆序执行即可。

原理六：GPU-Initiated RDMA 的零 CPU 开销 硬件

DeepEP V2 使用 NCCL Gin backend 实现 GPU 直接发起 RDMA 操作：

// dispatch.cuh L388-391: RDMA put 由 GPU warp 直接发起
gin.put<team_t>(recv_buffer.get_token_buffer(stored_dst_slot_idx).get_base_ptr(),
                send_buffer_ptr, tma_buffer.get_num_bytes<false>(), stored_dst_rank_idx);

这消除了传统 RDMA 需要的 CPU 代理开销，实现了 kernel-level all-to-all。

2.2 ElasticBuffer 统一抽象

ElasticBuffer 是 V2 的核心抽象，统一了：

  • High-throughput EP：NVLink + RDMA all-to-all
  • Low-latency EP：RDMA one-sided
  • Engram：远程 KV cache 获取
  • PP send/recv：流水线并行
  • AGRS：All-gather/Reduce-scatter

2.3 Scale-up / Scale-out 分层

DeepEP 将 EP 域分为两层：

  • Scaleup：NVLink 连接的 rank（通常 8 个/node），全带宽通信
  • Scaleout：RDMA 连接的 scaleup 组，带宽受限

Hybrid mode 利用这一分层，在 scaleup 域内做 reduction，减少 scaleout 通信量。

三、代码深度分析

3.1 Dispatch Kernel 的三阶段流水线

Dispatch kernel（dispatch.cuh）是 DeepEP 最复杂的组件，分为三个阶段：

Phase 1: Notify Warps — 路由计数与通知
// dispatch.cuh L79-107: Notify warps 统计每个 expert 和 rank 的 token 数量
for (int i = global_warp_idx; i < num_tokens; i += kNumNotifyWarps * kNumSMs) {
    const auto dst_expert_idx = lane_idx < kNumTopk ?
        static_cast<int>(__ldg(topk_idx + i * kNumTopk + lane_idx)) : -1;
    if (dst_expert_idx >= 0)
        atomicAdd_block(expert_count + dst_expert_idx, 1);
    // Rank choice with deduplication
    const auto dst_rank_idx = dst_expert_idx >= 0 ? dst_expert_idx / kNumExpertsPerRank : -1;
    if (ptx::deduplicate(dst_rank_idx, lane_idx) and dst_rank_idx >= 0)
        atomicAdd_block(rank_count + dst_rank_idx, 1);
}

Notify warps 使用 shared memory atomic 进行本地计数，然后通过 ptx::red_add 进行全局 reduction，最后通过 NCCL Gin 将 count 写入对端。

Phase 2: Dispatch Warps — TMA Load + Slot Allocation
// dispatch.cuh L287-351: TMA 加载 token 数据 + atomic slot 分配
ptx::tma_load_1d(tma_buffer.get_hidden_ptr(), ..., kNumHiddenBytes);
// ...
stored_dst_slot_idx = atomicAdd(workspace_layout.get_scaleup_atomic_sender_counter()
                                + stored_dst_rank_idx, 1);

每个 dispatch warp 独立处理 token，使用 TMA 从全局内存加载 hidden 数据到 shared memory，然后通过 atomicAdd 分配目标 slot。

Phase 3: TMA Store / RDMA Put — 数据发送
// dispatch.cuh L372-393: NVLink TMA store 或 RDMA put
if (dst_ptr != nullptr)
    ptx::tma_store_1d(dst_ptr, tma_buffer.get_base_ptr(), ...);  // NVLink
else
    gin.put<team_t>(recv_buffer..., send_buffer_ptr, ..., stored_dst_rank_idx);  // RDMA

根据目标 rank 是否 NVLink 可达，选择 TMA store（零拷贝）或 RDMA put（通过 send buffer）。

3.2 TokenLayout 内存布局

TokenLayout 定义了单个 token 在通信 buffer 中的布局：

// layout.cuh L179-248: TokenLayout 结构
struct TokenLayout {
    int num_hidden_bytes;      // hidden_size * dtype_size (e.g., 7168*2=14336)
    int num_sf_bytes;          // FP8 scale factor bytes
    int num_topk;              // top-k indices
    int num_metadata_bytes;    // topk_idx + weights + src_token_global_idx

    // 内存布局 (TMA aligned):
    // | hidden (aligned) | SF (aligned) | metadata (aligned) | mbarrier (if with) |
};

关键设计：所有段都 TMA 对齐（128 bytes），确保 TMA load/store 的正确性。

3.4 Deterministic Sort 的数值分析动机

FP8 加法不满足结合律，导致不同到达顺序的 token 累加结果不同。DeepEP 通过 deterministic sort 保证训练可复现：

// elastic.py L100-163: deterministic_sort
// 非 expand 模式：按 src_token_global_idx 排序所有接收到的 tensor
// expand 模式：按 (expert_idx, src_token_global_idx) 排序
orig_indices = torch.sort(sort_keys).indices
permute(recv_x, orig_indices)
permute(recv_topk_weights, orig_indices)

3.5 SM 数量的理论计算模型

DeepEP V2 使用 analytical model 计算最优 SM 数量，无需 auto-tuning：

// elastic.py L728-834: get_theoretical_num_sms
# 计算期望 top-k（balanced gate）
num_expected_topk = num_groups * (1 - C(E-E/g, K) / C(E, K))

# 计算各维度流量
sm_read = 1 / num_expected_topk
sm_write = ...
rdma_traffic = ...
nvlink_traffic = ...

# 找到瓶颈
bounded_traffic = max(rdma_traffic, nvlink_traffic)
bounded_gbs = corresponding bandwidth

# SM 数量 = 瓶颈带宽需求 / 每 SM 带宽能力
num_sms = max(bounded_gbs/traffic * sm_read/sm_read_gbs,
              bounded_gbs/traffic * sm_write/sm_write_gbs)
num_sms = align(max(4, ceil(num_sms * 1.25)), 2)

四、核心问题深度回答

4.1 为什么要做 Token 重组？（Why Reorganize?）

这是三个 agent 从不同角度共同回答的核心问题。综合三视角，根本原因如下：

综合结论：Token 重组是 MoE 条件计算的数学必然，根植于以下三个不可调和的矛盾：

（a）GEMM 的连续内存要求 vs Routing 的随机到达

下游 expert GEMM 要求同一 expert 的 token 在内存中连续排列。但 dispatch 完成后，token 按到达顺序排列（来自不同 rank 的不同 token 交错），而非按 expert ID 排序。这是一个 permutation 操作，无法避免。

（b）Expert Alignment 的 padding 需求

为实现高效的 GEMM（如 128 对齐），每个 expert 的 token 数需要对齐到 expert_alignment。这进一步要求重组时插入 padding。

（c）FP8 精度与 Determinism

FP8 加法不满足结合律，不同累加顺序产生不同结果。为保证训练可复现，必须按确定性顺序排列 token。

三视角分歧：
  • Agent 1（架构）：硬件约束最具决定性——expand mode 的复制策略只在带宽受限时才合理
  • Agent 2（代码）：重组是 write-time（atomic slot allocation）和 copy-time（epilogue kernel）两阶段的权衡
  • Agent 3（理论）：本质是从高熵布局到低熵布局的转换，根植于 MoE 条件计算的数学本质
综合判断：三者互补——数学约束定义了下界，硬件约束决定了具体实现，代码实现是两者的工程折中。

4.2 为什么一定是随机访存？（Why Random Access?）

综合结论：随机访存不是设计选择，而是 MoE routing 的数学本质决定的。

数学证明

设 token $t$ 选择 expert $e$ 的概率为 $p(e|t) = \text{softmax}(W_g \cdot x_t)$。对于不同的 token $t_1 \neq t_2$，其 routing 决策是条件独立的：

$$p(e_1 \mid t_1) \perp p(e_2 \mid t_2), \quad \text{for } t_1 \neq t_2$$

因此，token $t$ 的目标 rank $r(t) = e(t) / E_{per\_rank}$ 是一个随机变量，其分布取决于 Gate 网络的输出。对于 balanced gate：

$$P(r(t) = r) = 1 / \text{num\_ranks}, \quad \forall r$$

这意味着：

  • 无法预测下一个 token 的目标 rank
  • 任何预取策略的准确率上限为 $K/E$（对于 V3 配置约 3.1%）
  • 对目标 buffer 的写入模式是随机的

DeepEP 的应对策略

既然随机访存不可消除，DeepEP 通过以下机制隐藏随机访存的延迟：

机制作用代码位置
TMA 硬件卸载异步数据传输，不占用 SM 计算资源dispatch.cuh L287-291
Warp 特化notify warps 和 dispatch warps 并行执行dispatch.cuh L79-395
mbarrier 同步fine-grained producer-consumer 同步dispatch.cuh L271-359
QP 并发多个 Queue Pair 并行发送 RDMA 请求comm.cuh L56-86
Atomic slot allocation无锁并行写入，每个 warp 独立分配dispatch.cuh L344-350
三视角分歧：
  • Agent 2：强调 TMA/mbarrier/QP 硬件机制是应对核心，"不是让随机变顺序，而是让随机足够快"
  • Agent 3：强调信息论下界，预取准确率仅 ~0.4%，随机性是本质
  • Agent 1：承认不可避免，但 node-limited routing 可缓解
综合判断：Agent 2 的表述最精确——DeepEP 的设计哲学是"承认不可预测性，利用层次化带宽，逼近理论极限"。

4.3 为什么 Combine 可以顺序？（Why Sequential Combine?）

Combine 是 Dispatch 的逆操作，但访问模式完全不同：

  • Dispatch：写随机（目标 slot 不可预测）→ 需要 atomic allocation
  • Combine：读顺序（按接收顺序遍历）+ 写随机（目标 rank 不可预测）

Combine 能顺序读取是因为 dispatch 阶段已将 routing 信息保存在 recv_src_metadata 中。但 Agent 2 指出：combine 的写入仍然是随机的（目标 rank 不可预测），只是读取可以是顺序的。

七、交叉讨论记录

三个 agent 在完成独立报告后，互相审阅了对方的工作并进行了交叉讨论。以下是讨论的核心内容：

7.1 三方共识（5 个关键点）

  1. MoE Routing 的随机性是内生属性，不是工程缺陷，无法通过设计消除
  2. All-to-All 通信是系统瓶颈，计算-通信完全重叠是核心设计目标
  3. Node-Limited Routing 改变通信拓扑，将扁平 all-to-all 变为层次化 all-to-all
  4. EPHandle 是 routing 逆映射的缓存，其设计接近信息论下界
  5. FP8 低精度是 Deterministic Sort 的驱动力，解决非结合律导致的训练不可复现

7.2 主要分歧（3 个差异点）

分歧 1：重组的首要原因

  • Agent 1：硬件约束最具决定性
  • Agent 2：write-time vs copy-time 的工程权衡
  • Agent 3：从高熵到低熵的信息论转换
综合：三者互补，数学约束定义下界，硬件约束决定实现，代码是工程折中

分歧 2：Combine 是否"顺序"

  • Agent 1/3：Combine 可顺序执行
  • Agent 2：更精确表述是"读顺序、写随机"
综合：Agent 2 更精确，combine 的写入目标 rank 仍然是随机的

分歧 3：Expand Mode 的定位

  • Agent 3："sparse-to-dense 转换"是优雅的设计核心
  • Agent 2："8x 内存换带宽"是工程优化手段
综合：Expand mode 是内存-计算权衡的编译时选项，非普适设计原则

7.4 最终综合判断

关于"为什么要重组"：本质是从高熵布局到低熵布局的转换，根植于 MoE 条件计算的数学本质。GEMM 要求连续内存、expert alignment 要求 padding、FP8 要求确定性顺序——三重约束共同决定了重组不可避免。

关于"为什么一定是随机访存"：不是设计选择而是数学必然。MoE 的核心价值（条件计算）要求每个 token 独立选择 expert，预取准确率仅 ~0.4%。DeepEP 的设计哲学是"承认不可预测性，利用层次化带宽，逼近理论极限"——通过 TMA 硬件卸载 + warp 特化 + QP 并发将随机访存的延迟隐藏到接近零。
