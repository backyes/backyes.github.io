一、第一性原理分析

1.1 MoE Routing 的随机性本质

Mixture-of-Experts 的核心数学形式为：给定输入 token x，门控网络 G(x) 产生一个稀疏激活模式：

y = ∑i∈TopK(G(x)) Gi(x) · Ei(x)

其中 Ei 是第 i 个 expert 的变换，Gi(x) 是门控权重。==关键洞察==：门控输出 G(x) ∈ RN（N 为 expert 总数）是一个取决于输入的随机向量。在训练过程中，由于输入分布的随机性和 softmax 函数的特性，每个 token 被路由到哪个 expert 本质上是一个==随机事件==。

形式化地，定义 routing 指示变量：

Ri(x) = 1[i ∈ TopK(G(x))]

对于 expert 数量为 N、top-k 为 k 的 MoE 层，routing 过程定义了一个从 token 空间到 expert 空间的==随机映射== f: [T] → [N]k，其中 T 为 token 总数。

这种随机性导致三个核心问题：

  1. Load Imbalance：各 expert 接收的 token 数量不等，方差随 N 增大而增大
  2. Communication Pattern Uncertainty：token 到 rank 的映射是随机的，导致 all-to-all 通信量不确定
  3. Buffer Sizing：必须按最坏情况预分配接收 buffer

1.2 All-to-All Communication 的图论模型

EP 中的 dispatch（all-to-all）可以建模为一个==二分图上的流问题==：

G = (L ∪ R, E), L = {token positions}, R = {expert slots}

其中边 (t, e) 存在当且仅当 expert e 是 token t 的 top-k 选择。dispatch 过程等价于将每个 token 的数据沿边传输到对应的 expert 节点。

==定理（All-to-All 通信下界）==：在 P 个 rank 的系统中，设第 i 个 rank 需要向第 j 个 rank 发送 cij 字节，则完成 all-to-all 所需的最少时间为：

T ≥ max( maxi ∑j cij / Bout,   maxj ∑i cij / Bin )

其中 Bout 和 Bin 分别为节点的出/入带宽。这个下界表明：==all-to-all 的瓶颈取决于最忙的发送者或最忙的接收者==。

在 DeepEP 中，这个模型进一步分层为：

  • Scale-up 域（NVLink）：高带宽（~900 GB/s），低延迟，全连接拓扑
  • Scale-out 域（RDMA）：低带宽（~100-400 GB/s），高延迟，可能非全连接

这对应于一个==层次化的 all-to-all==，其通信图是 scale-up clique 和 scale-out bipartite graph 的复合。

1.3 Token Permutation 的信息论下界

Dispatch 的核心操作是一个==token permutation==：将分布在各 rank 上的 token 重新排列，使得同一 expert 的所有 token 连续存放于该 expert 所在的 rank 上。

设总 token 数为 T，hidden dimension 为 H，数据类型大小为 s bytes。则 dispatch 必须传输的数据总量为：

Dtotal = T · H · s · (1 - 1/P)   （均匀路由下）

==信息论视角==：token permutation 是一个确定性的可逆映射。对于接收端而言，为了正确还原每个 token 的身份，必须附带足够的 metadata。定义 routing 矩阵 M ∈ {0,1}T×N，其中 Mt,i = 1 表示 token t 路由到 expert i。则 routing 的熵为：

H(routing) = -∑t,i P(Mt,i=1) · log P(Mt>i=1)

对于均匀 top-k routing，P(Mt,i=1) = k/N，因此：

H(routing) = T · log(N/k) · k   bits

这意味着==接收端至少需要 T · k · ⌈log2N⌉ bits 的 metadata 来唯一标识每个 token 的来源==。DeepEP 的 recv_src_metadata 正是这个信息论下界的具体实现。

1.4 Load Balancing 与通信量的权衡

MoE 中 load balancing 的核心权衡可以形式化为一个==约束优化问题==：

min   ∑i |ni - T/N|
s.t.   ni = ∑t Ri(xt),   ∑i Ri(xt) = k

其中 ni 是第 i 个 expert 接收的 token 数。

==关键权衡==：

  • 辅助损失（Auxiliary Loss）：通过修改训练目标来惩罚不均衡，但会降低模型质量
  • Capacity Factor：限制每个 expert 的最大 token 数，导致 token dropping 或 overflow
  • 确定性均衡（DeepSeek-V3）：通过 auxiliary-loss-free 策略在 gating 中直接引入 bias，不修改损失函数

在 EP 的语境下，不均衡路由导致：

Commactual = ∑i≠j cij   ≤   Commbalanced · α   (α > 1 为不均衡因子)

DeepEP 通过 ==elastic buffer== 机制来处理这种不均衡：buffer 按最大可能 token 数预分配，实际使用量通过 prefix sum 动态计算。

1.5 Communication-Computation Overlap 的理论极限

DeepEP 的一个核心设计目标是 ==0 SM occupation==（或极少 SM），即通信内核几乎不占用计算资源，使得通信可以与 GEMM 计算完全 overlap。

==Amdahl 视角的 overlap 极限==：设 GEMM 计算时间为 Tgemm，通信时间为 Tcomm，SM 占用为 Scomm，则有效端到端时间为：

Te2e = Tgemm + Tcomm - overlap(Tgemm, Tcomm) + Scomm · Tsm

其中 overlap(Tgemm, Tcomm) = min(Tgemm, Tcomm)。

==理论最优==：当 Tgemm ≥ Tcomm 且 Scomm → 0 时，通信完全被隐藏。DeepEP 通过以下方式逼近这个极限：

  1. 使用 RDMA（zero-copy）或 NCCL Gin backend 减少 SM 占用
  2. Analytical SM count model（get_theoretical_num_sms）精确计算最小所需 SM
  3. Event-based async API 允许 compute stream 与 comm stream 并行

代码中的 bandwidth model 推导：

SMoptimal = max( Bbounded / Trafficbounded · SMread / SMread_gbs,   Bbounded / Trafficbounded · SMwrite / SMwrite_gbs )

这是一个==roofline model==的变体，通过比较通信带宽瓶颈和 SM 读写带宽瓶颈来确定最优 SM 数量。

二、DeepSeek 论文中的 EP 设计决策

2.1 DeepSeek-V2 的 MoE 架构与 EP

DeepSeek-V2（236B 总参数，21B 激活参数）采用了 DeepSeekMoE 架构，其关键特征：

  • Fine-grained Expert：将 expert 切分为更细粒度，提高 expert 利用率
  • Shared Expert：设置部分"共享 expert"处理通用知识，减少路由开销
  • Top-8 Routing：每个 token 选择 8 个 expert

从 EP 视角，DeepSeekMoE 的设计意味着：

RoutingV2: x → TopK(G(x), k=8),   G(x) ∈ R160   (约 160 experts)

==关键设计决策==：DeepSeek-V2 使用了 ==auxiliary loss== 来强制 load balance。这影响了 EP 的通信模式——由于 auxiliary loss 使得路由趋于均匀，通信量更可预测，buffer sizing 更保守。

2.2 DeepSeek-V3 的 Node-Limited Routing

DeepSeek-V3（671B 总参数，37B 激活参数）引入了革命性的设计：

DeepSeek-V3 pioneers an auxiliary-loss-free strategy for load balancing and sets a multi-token prediction training objective for stronger performance.

==Node-Limited Routing 的数学含义==：

传统 routing 允许 token 路由到任意 rank 上的 expert。Node-limited routing 将选择约束在同一个 node（scale-up 域）内：

TopKV3(G(x)) = TopK( G(x) + Bnode ),   Bnode,i = { +∞ if expert i in local node, 0 otherwise }

这意味着：

  • Scale-up 通信量 ↑：更多 token 通过 NVLink 传输（高带宽，低延迟）
  • Scale-out 通信量 ↓：RDMA 传输减少（低带宽，高延迟）
  • 总通信延迟 ↓：因为 NVLink 带宽是 RDMA 的 ~5-10x

代码中 get_theoretical_num_sms 的注释明确提到：

# For V3.0's group-limited gate, please do not use this function
# TODO: support this
assert num_scaleout_topk == 0

这表明 DeepEP 当前的 analytical model 尚未完全适配 V3 的 group-limited gate，但代码架构已为此预留了扩展空间。

2.3 Auxiliary-Loss-Free Load Balancing 对 EP 的影响

DeepSeek-V3 的 auxiliary-loss-free 策略通过直接在 gating 中添加 per-expert bias 来实现均衡：

GatingV3(x)i = Softmax( Wg · x + bi )i

其中 bi 是一个可学习的 bias，动态调整以维持各 expert 的负载均衡。

==对 EP 通信模式的影响==：

  1. 路由更确定性：由于 bias 是确定性参数，相同 token 的路由更稳定
  2. 通信量更可预测：负载均衡意味着各 rank 间的通信量趋于均匀
  3. Buffer sizing 更激进：可以按平均情况而非最坏情况分配 buffer
  4. 训练-推理一致性：无 auxiliary loss 意味着训练时的路由分布更接近推理时

代码中 cumulative_local_expert_recv_stats 参数正是为了在线监控这种负载均衡程度而设计的。

2.4 Group-Limited Gating 的数学分析

Group-limited gating 是 DeepSeek-V3 的核心创新之一。其数学形式为：

Gatinggroup(x) = Softmax( Wg · x )   →   GroupSelect( · , g groups, k' per group )

即将 N 个 expert 分为 g 个 group，先在每个 group 内选择 top-k'，再在全局选择 top-k。这产生了一个==层次化的 routing 结构==：

P(token → expert in remote node) < P(token → expert in local node)

这种层次化结构使得 EP 通信呈现==两阶段特征==：

  • 阶段 1（Scale-up）：通过 NVLink 在 node 内传输，高带宽
  • 阶段 2（Scale-out）：通过 RDMA 跨 node 传输，低带宽

DeepEP 的 hybrid mode 正是为此设计的：先用 RDMA 将数据发送到目标 node，再在 node 内通过 NVLink 广播。

三、核心问题深度回答

3.1 为什么要重组？（Why Reorganize?）

Dispatch 完成后，接收端获得的数据需要从"按到达顺序排列"重组为"按 expert 分组排列"。这涉及三个层面的原因：

(a) Token Routing 的数学本质

MoE 的数学形式要求同一 expert 的所有 token 被一起处理：

Ei({xt : t ∈ Ωi}),   Ωi = {t : i ∈ TopK(G(xt))}

如果 token 不按 expert 分组，则需要额外的 indirection 来索引每个 expert 对应的 token 子集，这在计算上是低效的。

(b) Memory Coalescing

GPU 的 global memory 访问以 32-byte 或 128-byte 的 sector 为单位。当同一 expert 的 token 连续存储时，GEMM 操作可以实现==完全合并访问（coalesced access）==：

Effective Bandwidth = ∑i BWcoalesced · utili
utili = 1 if stride = 1,   utili < 1 if stride > 1

DeepEP 的 expert_alignment 参数确保每个 expert 的 token 数对齐到特定值（如 128），进一步优化 memory access pattern。

(c) GEMM 布局要求

MoE 的 FFN 层通常实现为 grouped GEMM 或 batched GEMM，要求输入 tensor 的维度为 [num_tokens_for_expert_i, hidden]。Expand mode 直接产生这种布局：

recv_x = [   tokens_for_expert_0   |   tokens_for_expert_1   |   ...   |   tokens_for_expert_N   ]

代码中 psum_num_recv_tokens_per_expert 正是这个布局的 offset 索引。

3.2 为什么一定是随机访存？（Why Random Access?）

Combine 阶段需要将 expert 输出发送回原始 token 所在的 rank。这个过程涉及==随机访存==，原因如下：

(a) MoE Gating 的概率分布

门控网络的输出 G(x) ∈ RN 是一个取决于输入 x 的随机向量。即使两个 token 来自同一 rank，它们的 top-k expert 选择几乎必然不同：

P(topk(x1) = topk(x2)) = C(N-k, k) / C(N, k) ≈ (1 - k/N)k

对于 N=256, k=8，这个概率约为 0.788 ≈ 0.13，即只有 13% 的概率两个 token 有完全相同的路由。

(b) Token 到 Expert 的映射关系

Dispatch 建立的映射 f: token → expert 是多对多的：一个 token 映射到 k 个 expert，一个 expert 接收多个 token。其逆映射 f-1: expert_slot → (src_rank, src_token) 就是 combine 需要的信息。

这个逆映射存储在 recv_src_metadata 中，其结构为：

recv_src_metadata[i] = [   src_token_global_idx,   src_rank_topk_idx,   slot_0, slot_1, ..., slot_{k-1}   ]

(c) Graph Theory 角度

从图论视角，dispatch 建立了一个==二分图== G = (Tokens, Experts, Edges)。Combine 是这个二分图的==反向遍历==：从 expert 侧出发，沿反向边回到 token 侧。

由于二分图的度分布不均匀（某些 expert 连接很多 token，某些很少），combine 的写入模式是==不规则的（irregular）==，即对目标 rank 的写入位置取决于 routing 结果，无法预测。这就是随机访存的本质。

3.3 为什么 Combine 可以顺序？（Why Sequential Combine?）

这是一个深刻的观察。尽管 combine 涉及随机访存，但 DeepEP 的 combine kernel 可以按==顺序遍历==接收到的 token，原因在于：

(a) Dispatch/Combine 的对称性

Dispatch 和 combine 是==时间反转对称==的操作：

  • Dispatch：按 token 顺序读取 → 按 expert 位置写入（scatter）
  • Combine：按接收顺序读取 → 按原始位置写入（scatter）

关键在于：combine 的"顺序"是指遍历接收 buffer 的顺序（即 dispatch 后的存储顺序），而非原始 token 顺序。

(b) Routing 的可逆性

Dispatch 过程中存储的 metadata 包含了完整的 routing 逆映射。Combine 只需按顺序读取每个接收到的 token，查找其 metadata 中的源位置，然后写入对应位置：

combine(recv_x[i]) → output[ src_metadata[i].src_rank ][ src_metadata[i].src_token ]

这是一个==间接寻址（indirect addressing）==操作。虽然写入是随机的，但读取是顺序的，因此 combine kernel 的内存访问模式是==读顺序、写随机==。

(c) 代码验证

combine.cuh 的核心循环证实了这一点：

for (int i = token_start_idx; i < token_end_idx; ++ i) {
    // 顺序读取 src_metadata
    const int src_token_idx = __ldg(src_metadata + i * kMetadataStride) % kNumMaxTokensPerRank;
    const int src_rank_topk_idx = __ldg(src_metadata + i * kMetadataStride + 1);
    // ... 写入目标位置（随机）
}

3.4 Expand Mode 的数学含义

Expand mode 是 DeepEP 的一个核心创新。其数学本质是==sparse-to-dense 转换==。

(a) Sparse-Dense 转换

在非 expand 模式下，接收 buffer 中的 token 是紧凑排列的（可能有 alignment padding）。在 expand 模式下，每个 token 被复制 k 次（k = top-k），每个副本对应一个 expert slot：

Non-expand:   recv_x ∈ RM×H,   M = total_received_tokens
Expand:   recv_x ∈ RM·k×H,   每个 token 出现 k 次

==关键洞察==：expand mode 将"哪个 token 去哪个 expert"的 routing 信息==编码到位置==中：

recv_x[ psum[i] + j ] = token_assigned_to_expert_i_slot_j

这意味着 GEMM 可以直接使用 recv_x 作为输入，无需额外的 indexing 操作。

(b) Expert-Local Data Layout

Expand mode 产生的布局是==expert-local==的：属于同一 expert 的所有 slot 连续存放：

recv_x = ⊕i=0N-1 [ sloti,0, sloti,1, ..., sloti,k-1 ]

其中 ⊕ 表示 concatenation。这种布局使得：

  • GEMM 可以直接用 psum_num_recv_tokens_per_expert 作为 offset
  • 每个 expert 的 GEMM 是独立的，可以并行执行
  • Padding（alignment）只影响每个 expert 组的末尾，不影响其他 expert

(c) 代码中的 Expand 实现

dispatch_copy_epilogue.cuh 中的 expand 逻辑：

} else if (kDoExpand and not kCachedMode and dst_expert_idx >= 0) {
    dst_tensor_idx = atomicAdd(psum_num_recv_tokens_per_expert + dst_expert_idx, 1);
}

这使用原子操作来分配每个 expert 内的 slot 位置，确保同一 expert 的 token 被连续写入。

四、EPHandle 的数学结构分析

EPHandle 是 dispatch 和 combine 之间的==桥梁==，包含了 routing 的完整元数据。下面分析其核心字段的数学含义。

4.1 psum_num_recv_tokens_per_scaleup_rank 的 Prefix Sum 含义

这是一个==inclusive prefix sum==数组，记录每个 scale-up rank 累计接收的 token 数：

psum[i] = ∑j=0i count[j],   count[j] = tokens received from scale-up rank j

其核心作用：

  • Buffer 定位：recv_buffer[rank_i][ psum[i-1] ... psum[i]-1 ] 即为来自 rank_i 的所有 token
  • Total count：psum[last] 等于总接收 token 数
  • Rank 遍历：combine kernel 使用这个数组来确定每个接收 token 来自哪个 rank

代码中的 prefix sum 实现（dispatch.cuh）：

const auto do_psum = [=](const int* count, int* out, const int n, const int is_exclusive) {
    int psum = 0;
    for (int i = 0; i < ceil_div(n + is_exclusive, 32); ++ i) {
        const auto idx = i * 32 + lane_idx;
        const auto value = (0 <= mem_idx and mem_idx < n) ? count[mem_idx] : 0;
        const auto sum = psum + ptx::warp_inclusive_sum(value, lane_idx);
        if (idx < n + is_exclusive) out[idx] = sum;
        psum = ptx::exchange(sum, 31);
    }
};

这是一个==warp-level parallel prefix sum==，利用 NVIDIA warp shuffle 指令实现 O(log n) 复杂度的并行扫描。

4.2 psum_num_recv_tokens_per_expert 的布局含义

这是一个更精细的 prefix sum，记录每个 local expert 的累计 token 数（含 alignment padding）：

psum_exp[i] = ∑j=0i-1 align(count[j], A)   (exclusive prefix sum, A = expert_alignment)

==非 expand 模式==：这是 inclusive prefix sum，psum_exp[i] 是 expert i+1 的起始 offset。

==Expand 模式==：这是一个==混合 prefix sum==，其定义为：

psum_exp[i] = align(psum_exp[i-1], A) + count[i]

这意味着：

  • psum_exp[i] - align(psum_exp[i-1], A) = expert i 的实际 token 数
  • align(psum_exp[i], A) = expert i+1 的起始 offset

这种设计使得 expand mode 可以同时支持：

  1. 对齐的 GEMM 输入（通过 padding）
  2. 精确的实际 token 数（通过差值恢复）

4.3 recv_src_metadata 的 Routing 逆映射作用

recv_src_metadata 是 EPHandle 中最核心的字段，存储了==routing 的逆映射==。其结构为：

recv_src_metadata[i] = [   src_global_idx,   src_rank_topk,   slot_0, slot_1, ..., slot_{k-1}   ]

各字段含义：

  • src_global_idx = rank_idx * num_max_tokens_per_rank + token_idx：全局唯一的源 token 标识
  • src_rank_topk = src_rank_idx * k + topk_lane_idx：源 rank 和 top-k lane 的复合索引
  • slot_j（expand mode）：该 token 在 expert j 的 expand buffer 中的位置

==数学本质==：这是一个==置换矩阵的压缩表示==。定义 dispatch 置换 σ: [M] → [M]，其中 M 是总接收 token 数，则：p>

σ(dispatch_order_idx) = (src_rank, src_token, src_topk)

Combine 使用这个逆置换将 expert 输出发送回正确的位置。

4.4 deterministic_sort 的数学原理

当 deterministic=True 时，DeepEP 保证相同输入产生相同的 dispatch 输出，不受接收顺序影响。其原理是==基于 source token global index 的排序==：

sort_key[i] = recv_src_metadata[i].src_global_idx
sorted_order = argsort(sort_key)

==非 expand 模式==：直接对所有接收到的 token 按 source global index 排序，然后重排 recv_x、recv_sf、recv_topk_weights、recv_topk_idx 和 recv_src_metadata。

==Expand 模式==：需要更精细的排序，因为 expand buffer 的布局是 expert-grouped 的。排序 key 的设计为：

sort_key_expanded = expert_idx · MAX + (-MAX) + src_global_idx   (valid tokens)
sort_key_expanded = expert_idx · MAX   (padding slots)

这保证了==先按 expert 分组，再按 source global index 排序==，且 padding 排在 valid tokens 之后。

==为什么需要 deterministic？==

  1. 训练可复现性：相同输入必须产生相同输出以支持调试
  2. 数值稳定性：FP8 加法不满足结合律，顺序影响结果
  3. 分布式一致性：不同 rank 的 partial reduction 需要确定性顺序

五、与 DeepSeek-V3 的关联

5.1 Node-Limited Routing 如何影响 EP 设计

DeepSeek-V3 的 node-limited routing 对 EP 设计产生了==根本性影响==：

(a) 通信拓扑的变化

传统 EP：all-to-all 在所有 rank 间均匀发生。

Node-limited EP：通信呈现==层次化==特征：

Commtotal = Commscale-up + Commscale-out Commscale-up ≫ Commscale-out   (node-limited 下)

DeepEP 的 hybrid mode 正是为此优化：

  • Scale-up 使用 NVLink（~900 GB/s per GPU）
  • Scale-out 使用 RDMA（~400 GB/s per NIC）
  • Hybrid mode 在每个 node 内先聚合，再跨 node 传输

(b) Buffer 设计的变化

Node-limited routing 使得 buffer sizing 可以==更精确==：

Buffernode-limited ≈ T · k · (1 - 1/G) · H · s

其中 G 是 node 内的 rank 数。相比传统 routing 的 T · k · (1 - 1/P) · H · s（P 为总 rank 数），buffer 需求减少约 (P-G)/(P-1) 倍。

(c) SM Count Model 的变化

代码中的 get_theoretical_num_sms 函数包含了对 scale-up/scale-out 的分别建模：

SMread = 1/expected_topk   (HBM read for token loading)
SMwrite = f(scaleup_traffic, scaleout_traffic)
bounded = max(rdma_traffic/rdma_gbs, nvlink_traffic/nvlink_gbs)

对于 node-limited routing，expected_scaleout_topk 显著减小，从而：

  • Scale-out RDMA 流量减少 → 通信瓶颈减轻
  • 所需 SM 数减少 → 更多 SM 可用于计算
  • Overlap 更容易实现 → 端到端延迟降低

5.2 Expert Parallelism Degree 与 Model Quality 的关系

EP degree（即 rank 数 P）与 model quality 之间存在==非线性关系==：

(a) 正面效应

  • 更大 expert 池：更多 expert 意味着更细粒度的 specialization
  • 更低激活比：每个 token 激活的参数占比更低，计算更高效
  • 更高 throughput：每个 rank 只处理部分 expert，GEMM 更小

(b) 负面效应

  • 更多通信：all-to-all 通信量随 P 增加（虽然 per-rank expert 数不变）
  • 路由稀疏性：更大的 N 使得 top-k 选择更稀疏，expert 利用率可能下降
  • 训练不稳定：auxiliary loss 或 bias 需要更精细的调优

(c) 定量分析

对于 DeepSeek-V3 的配置：

P = 256   (EP degree)
N = 256   (total experts)
k = 8   (top-k)
Experts per rank = 1   (N/P = 1)

==关键观察==：当 N/P = 1 时，每个 rank 只有一个 local expert。这意味着：

  • Dispatch 后，每个 rank 只需处理自己 expert 的 token
  • GEMM 是标准的 dense GEMM，无需 grouped GEMM
  • Combine 的写入目标完全由 routing 决定（最大随机性）

根据 README 中的性能数据（V3 配置：8K tokens/batch, H=7168, top-8, FP8）：

六、关键数据流与内核机制

6.1 Notify Warps 的计数逻辑

dispatch.cuh 使用 notify warps 来==并行统计 routing 分布==。其核心思想是：

Phase 1:   atomicAdd_block(expert_count + dst_expert_idx, 1)   // 每个 SM 本地计数
Phase 2:   red_add(workspace + i, (1<<32) | count)   // 全局归约
Phase 3:   wait_for_all_SMs()   // 等待所有 SM 完成
Phase 4:   prefix_sum()   // 计算 offset

==关键设计==：使用 64-bit atomic 的高 32 bit 作为==arrival counter==，低 32 bit 作为==value accumulator==。这允许在一个 atomic 操作中同时完成"报告到达"和"累加值"：

encoded = (num_arrivals << 32) | value
wait_condition: (encoded >> 32) == kNumSMs

6.2 Dispatch Copy Epilogue 的 Expand 逻辑

dispatch_copy_epilogue.cuh 是 dispatch 的==第二阶段==，负责将接收 buffer 中的数据重组到输出 tensor。其 expand mode 的核心逻辑：

} else if (kDoExpand and not kCachedMode and dst_expert_idx >= 0) {
    dst_tensor_idx = atomicAdd(psum_num_recv_tokens_per_expert + dst_expert_idx, 1);
}

这实现了==per-expert slot 分配==：每个 expert 维护一个 atomic counter，新到达的 token 原子地获取一个 slot index。这保证了：

  • 同一 expert 的 token 连续存放
  • 无需全局同步（只需 block-level atomic）
  • 支持 dynamic token count（无需预知每个 expert 的 token 数）

6.3 Combine 的逆过程

combine.cuh 实现了 dispatch 的==精确逆操作==。其核心循环：

for (int i = token_start_idx; i < token_end_idx; ++ i) {
    const int src_token_idx = __ldg(src_metadata + i * kMetadataStride) % kNumMaxTokensPerRank;
    const int src_rank_topk_idx = __ldg(src_metadata + i * kMetadataStride + 1);
    const int src_rank_idx = src_rank_topk_idx / kNumTopk;
    // ... TMA store to remote or local
}

==三种 combine 模式==：

  1. No expand + no reduce：直接发送，无本地 reduction
  2. Expand + reduce：多个 slot 的输出需要本地 reduce 后再发送
  3. Expand + send all：每个 slot 独立发送（用于 backward）

==Multiple Reduction 的数学含义==：当 kAllowMultipleReduction=true 时，combine 在本地先对同一 token 的多个 expert 输出进行 reduce，然后再发送。这减少了通信量但增加了本地计算：

Commmulti-reduce = Commno-reduce / k   (per token)
Computemulti-reduce = Computeno-reduce + k · H · f_add

6.4 Hybrid Mode 的层次化通信

DeepEP 的 hybrid mode 实现了==层次化 all-to-all==：

Phase 1 (Scale-up):   local_rank → node_aggregator   via NVLink
Phase 2 (Scale-out):   node_aggregator → remote_node   via RDMA
Phase 3 (Scale-up):   remote_node → local_rank   via NVLink

这种设计的==理论优势==：

  • 利用 NVLink 高带宽进行 node 内聚合
  • RDMA 只传输聚合后的数据，减少跨 node 流量
  • Node 内聚合可以==去重==（同一 token 的多个 expert 在同一 node 时只发送一次）

代码中的 QP（Queue Pair）分配策略反映了这一点：

if (self.allow_hybrid_mode):
    num_allocated_qps = 65 if check_fast_rdma_atomic_support() else 129
else:
    num_allocated_qps = 17

Hybrid mode 需要更多 QP（65-129 vs 17），因为每个 channel 和 notify 都需要独立的 QP。

A.2 关键思考过程

思考 1：为什么 EPHandle 需要缓存？

在推理 decoding 阶段，如果 gating 决策不变（如 shared expert 或 deterministic routing），则 routing metadata 可以跨 iteration 复用。EPHandle 的缓存机制避免了重复的 CPU sync 和 layout computation，将 dispatch 的 overhead 从 O(T) 降低到 O(1)。

思考 2：Expand mode 的 trade-off

Expand mode 以内存换 simplicity：将 token 复制 k 倍使得 GEMM 可以直接使用连续内存，但增加了 k 倍的 buffer 需求。对于 k=8，这意味着 8x 的接收 buffer。这是否值得？答案是 yes，因为：(1) GEMM 效率提升远超内存成本，(2) 避免了 grouped GEMM 的 indexing overhead，(3) 支持 alignment padding 优化 memory access。

思考 3：Deterministic sort 的必要性

FP8 加法不满足结合律：(a + b) + c ≠ a + (b + c)。在分布式 reduce 中，不同 rank 的 partial sum 顺序不同会导致最终结果微小差异。Deterministic sort 确保所有 rank 使用相同的 reduction 顺序，保证训练的可复现性。

思考 4：Hybrid mode 的拓扑感知

Hybrid mode 的设计假设了 scale-up 域是全连接的（NVLink），而 scale-out 域是部分连接的（RDMA）。这种假设在 H800/H100 集群中成立：8 GPU 通过 NVLink 全连接，跨 node 通过 InfiniBand 连接。如果拓扑不同（如 PCIe 或 RoCE），hybrid mode 的优化可能不适用。

思考 5：SM count model 的局限性

当前的 get_theoretical_num_sms 假设 balanced gate，对于 V3 的 group-limited gate 不适用。这是因为 group-limited gate 改变了 routing 的概率分布，使得 scale-up/scale-out 的 traffic ratio 不再是简单的 1/(P-1)。
