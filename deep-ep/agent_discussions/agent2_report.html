一、第一性原理分析：GPU 硬件特性与设计原理

1.1 HBM 带宽瓶颈与计算-通信重叠

NVIDIA H100/H800 的 HBM3 带宽为 3.35 TB/s，NVLink-C2C 双向带宽 900 GB/s（18 links × 50 GB/s），RDMA (HDR InfiniBand) 单向 200 Gb/s = 25 GB/s（4× 聚合 100 GB/s）。

核心矛盾：MoE all-to-all 通信量与 token 数、hidden dim、top-k 成正比。DeepSeek-V3（256 experts, top-k=8, hidden=7168）：

单 token 数据量 = hidden × sizeof(bf16) + SF_pack + metadata
              = 7168 × 2 + 4×8 + (4+4+4×8) ≈ 14.4 KB
总通信量 (per GPU, 1024 tokens, top-k=8):
              = 1024 × 8 × 14.4 KB ≈ 115 MB

HBM 读取 115 MB 需 34 μs，RDMA 发送需 4.6 ms（25 GB/s）。通信延迟是计算的 100×+，必须实现计算-通信完全重叠。

1.2 五大核心设计原理

原理 1：TMA 硬件卸载数据搬运

Hopper 引入的 Tensor Memory Accelerator (TMA) 是专用 DMA 引擎：

  • 异步 1D/2D copy：cp.async.bulk 不占用 SM 计算资源
  • mbarrier 同步：硬件级 producer-consumer 同步
  • L2 cache hint：kEvictFirst / kEvictNormal
量化分析：TMA 1D bulk copy 可达 HBM 理论带宽 ~90%。14.4 KB token 数据 TMA load 约 4.3 μs，而 LDG 通过 SM 执行需额外寄存器压力和指令发射开销。TMA 释放 SM 的 LOAD/STORE 单元，使计算 warp 全速执行。

量化分析：H100 SM 有 4 个 warp scheduler，每周期可发射 2 条指令。通过 warp 特化，notify warp 的 Gin 指令、dispatch warp 的 TMA 指令、forward warp 的 RDMA 指令可在同一 SM 内并行发射，充分利用 4 warp scheduler × 2 issue slots = 8 inst/cycle。

原理 3：mbarrier 实现零开销 Producer-Consumer 同步

Hopperm 的 mbarrier 相比 __syncthreads()：

  • phase 翻转：每次 complete 自动翻转 parity，无需手动重置
  • expect_tx 语义：mbarrier.arrive.expect_tx 在 arrive 时声明写入字节数
  • try_wait 非阻塞：mbarrier.try_wait.parity 可轮询，不阻塞 warp scheduler
量化分析：__syncthreads() 需 barrier 到达所有线程后才放行，warp 级阻塞。mbarrier 的 try_wait 允许 warp 在等待期间被切换执行其他 warp（通过 dual-issue），实现 零周期 同步开销。实测 mbarrier 延迟约 20 cycles，__syncthreads 在 warp 发散时可达 100+ cycles。

Notify 阶段的 atomic 统计

 92// dispatch.cuh:92-108 - Atomic add on shared memory
 93constexpr int kNumTopk = 32;
 94const auto global_warp_idx = warp_idx * kNumSMs + sm_idx;
 95for (int i = global_warp_idx; i < num_tokens; i += kNumNotifyWarps * kNumSMs) {
 96    // Expert choice can not be redundant

 98        static_cast<int>(__ldg(topk_idx + i * kNumTopk + lane_idx)) : -1;
 99    if (dst_expert_idx >= 0)
100        atomicAdd_block(expert_count + dst_expert_idx, 1);
101    // Rank choice should do deduplication here
102    const auto dst_rank_idx = dst_expert_idx >= 0 ?
103        dst_expert_idx / kNumExpertsPerRank : -1;
104    if (ptx::deduplicate(dst_rank_idx, lane_idx) and dst_rank_idx >= 0)
105        atomicAdd_block(rank_count + dst_rank_idx, 1);

设计要点：

  • __ldg() 只读缓存加载 top-k indices，避免污染 L1
  • ptx::deduplicate() 通过 warp 内 match 指令去重，同一 rank 只计数一次
  • SMEM atomicAdd 比 GMEM atomicAdd 快 ~10×（4 cycles vs 40+ cycles）

2.3 Dispatch Copy Epilogue 的作用和必要性

dispatch_copy_epilogue 是独立 kernel（通过 cudaTriggerProgrammaticLaunchCompletion() 触发），核心职责：

  1. Token 重组：rank-major buffer → expert-major tensor
  2. Expand 模式：按 expert 维度展开 token
  3. Zero Padding：对齐 expert token 数到 kExpertAlignment
  4. Linked List 维护：hybrid 模式 per-channel 链表
为什么需要独立 kernel？
  1. Grid Dependency：cudaGridDependencySynchronize() 等待 dispatch 完成，避免长延迟 grid sync 阻塞 dispatch
  2. 并行执行：epilogue 可与 compute kernel 重叠（CUDA grid cooperation）
  3. 不同并行模式：dispatch 是 token-parallel，epilogue 是 slot-parallel，合并降低效率

3.3 Named Barrier 的使用

DeepEP 使用 PTX bar.sync 实现 warp 组内同步：

169// ptx.cuh:169-173 - Named barrier
170template <int kNumThreads>
171void named_barrier(const int& idx) {
172    asm volatile("bar.sync %0, %1;" :"r"(idx), "r"(kNumThreads));
173}

使用场景：notify warps 内部的阶段同步（dispatch.cuh:90, 108, 148, 181, 202, 221, 254）。kNotifyBarrierIndex = 1 是预分配的 barrier 索引。

为什么不用 __syncthreads()？
  • bar.sync 支持命名 barrier（0-15），不同 barrier 互不干扰
  • notify warps 只需组内同步（128 threads），不需全 block sync
  • 避免与 data warps 的 __syncthreads() 冲突

343    // 动态分配: atomicAdd 获取唯一 slot
344    if (ptx::deduplicate(stored_dst_rank_idx, lane_idx) and stored_dst_rank_idx >= 0)
345        stored_dst_slot_idx = atomicAdd(workspace_layout.get_scaleup_atomic_sender_counter()
346                                        + stored_dst_rank_idx, 1);
347}
atomicAdd 的作用：get_scaleup_atomic_sender_counter() 为每个 rank 维护一个单调递增的 sender counter。通过 atomicAdd，多个 warp 可并发地为同一 rank 分配唯一 slot index，无需锁。这是 lock-free 的 slot 分配策略。

4.4 2MB 对齐的原因

2MB 对齐的三个原因：
  1. NVL (NVLink) 大页映射：Hopper 使用 2MB 大页（Muge Table Entry）映射对称内存。2MB 对齐确保每个 buffer 映射到独立的大页，避免 TLB miss
  2. RDMA 注册粒度：IBV_REG_MR 要求内存注册按页对齐，2MB 对齐避免跨页访问的额外 DMA 事务
  3. NCCL VA space：NCCL 内部使用 4GB 对齐的虚拟地址空间（NCCL_WIN_STRIDE），2MB 对齐是最低要求

5.1 为什么要做 token 重组？

从内存访问模式角度分析：

┌─────────────────────────────────────────────────────────────────────┐ │ Token 重组的内存访问模式对比 │ ├─────────────────────────────────────────────────────────────────────┤ │ │ │ Dispatch 后 (Rank-Major): │ │ ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐ │ │ │ R0T0 │ R0T1 │ R1T0 │ R1T1 │ R2T0 │ R2T1 │ R3T0 │ R3T1 │ │ │ └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘ │ │ ↑ 同一 rank 的 token 连续，但 expert 分散 │ │ │ │ Combine 时需要: 同一 token 的多个 expert 结果加权求和 │ │ → 随机访问: R0T0→expert 5, R1T0→expert 5, R2T0→expert 5, ... │ │ → 无法合并内存访问 (coalesced access) │ │ │ │ ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄ │ │ │ │ Token 重组后 (Expert-Major, Expand Mode): │ │ ┌──────────────┬──────────────┬──────────────┬──────────────┐ │ │ │ Expert 0 │ Expert 1 │ Expert 2 │ Expert 3 │ │ │ │ T0,T3,T5,T8 │ T1,T4,T6,T9 │ T0,T2,T7,.. │ T1,T3,T5,.. │ │ │ └──────────────┴──────────────┴──────────────┴──────────────┘ │ │ ↑ 同一 expert 的 token 连续 │ │ │ │ Expert 计算时: 顺序读取同一 expert 的所有 token │ │ → 合并内存访问 (coalesced access) │ │ → 最大化 HBM 带宽利用率 │ └─────────────────────────────────────────────────────────────────────┘

量化分析：

  • Non-expand mode：token 按到达顺序排列，combine 时需 scatter 写入，带宽利用率 ~25%
  • Expand mode：token 按 expert 分组，combine 时 sequential 读取，带宽利用率 ~90%
  • 代价：需要额外 dispatch_copy_epilogue kernel 执行重组

5.2 为什么 dispatch 是随机访存？

从 MoE routing 的数学本质分析：

// MoE routing: 每个 token 选择 top-k experts
// gate(x) = Softmax(W_g · x)  ∈ R^{num_experts}
// topk_indices = TopK(gate(x), k)  ∈ [0, num_experts)^k
//
// 对于 expert e，接收的 token 集合:
// T_e = { token i | e ∈ TopK(gate(x_i)) }
//
// 由于 gate 的随机性，T_e 中的 token 在 batch 中随机分布
// → dispatch 写入 expert e 的 buffer 时，源地址随机 (gather)
// → combine 读取 expert e 的结果时，目标地址随机 (scatter)
随机访存的量化影响：
  • HBM burst length = 32 bytes (1 cache line)
  • 随机 8-byte 访问：带宽利用率 = 8/32 = 25%
  • 合并 32-byte 访问：带宽利用率 = ~90%
  • DeepEP 通过 TMA bulk copy (14.4 KB/burst) 缓解随机访问影响

6.1 为什么使用 JIT 而非预编译

JIT 编译的四大优势：
  1. 模板参数特化：kNumSMs, kNumQPs, kNumTopk 等编译期常量允许编译器展开循环、消除分支
  2. 硬件适配：根据实际 GPU 架构（H100/H800/A100）选择最优指令集
  3. 配置灵活：不同 MoE 配置（256 experts vs 64 experts）生成不同 kernel
  4. 编译缓存：jit::compiler->build() 缓存已编译 kernel，避免重复编译
